# Workflow

> How a change moves through this repo: the plan it starts as, the skills that carry it, the test every phase owes, and the gate it passes before it ships.

Work here starts as a written plan and ends as a released version, and the same path is followed by a person or an agent. The steps are kept as **skills** — one folder each under `.agents/skills/`, read by whatever is doing the work. A skill is typed with the host's own sign — `/ticket` in Claude, `$ticket` in Codex — and both spellings are accepted wherever one is read. `AGENTS.md` at the repo root is the standing guide they sit under, and it is where a rule that already cost a version number is written down.

## The order

**1. Plan it.** `/ticket` writes a Markdown plan — why, what was measured with the line it came from, how it is built, and phases with a checkbox per piece of work. Plans live in the `docs/` folder beside this repo, not in the published site. That planning tree keeps the live index at its root and the shipped, held and turned-down indexes beside the tickets in their matching folders, so each file opens on one status.

**2. Read the plan against the code.** `/design` opens every line the plan cites, holds it against the rules that already cost a version number, fixes what is wrong in the file, and signs the top with a date. It never edits app code. Where reading the code finishes a phase's own research it ticks those boxes and writes `Done in the design pass.` in that phase's reason, so the tick has an author.

**3. Rank it.** `/pm` puts every live plan into one running order — what is wrong today first, then what other plans are waiting on it, then how much a plan unblocks. What a plan waits on is declared once, in its own step's `Waits on` cell of the subject order it belongs to, and the running order's `Blocked by` and `Blocks` columns are computed from that rather than written by hand. A long band is cut in two on the reader's own question: the plans nothing stands in front of, then the ones waiting on a row above.

**4. Build it.** `/dev` works the phases in order and checks off each box as it is finished, one at a time along the way, in the same edit as the code and test that finish it — never batched at the end of a phase or of the build, and never ahead. It changes that box's `- [ ]` to `- [x]` with the host's own file-safe edit, and it never reaches the running app to do it: reading a plan through Leaftext brings that page to the front, so a tick took the owner's window and keyboard every time a box finished. The plan is the only place the owner can see a build happening, so a box left empty after its code is written reads as work that has not started. A change that moves something on the screen is proved by sampled positions rather than by classes — see [the motion probe](02-building.md#driving-the-copy-you-already-have-open).

**5. Gate it, once, when the owner asks.** A build stops when its last phase is built, and nothing calls the complete suite on the owner's behalf. `/test` is where they spend it: it takes the plans they name, or with none reads the running order for every row at `Dev` and keeps the ones with a box ticked — a plan dated as building whose boxes are all empty has landed nothing to prove. Then one `/sync-tests` across the whole batch, then one `just verify`, with a red fixed and the suite re-run from the top. The reading comes first because `just verify` only runs the tests that exist, and a change with no test passes it and proves nothing. One run answers for every plan in the batch, because every step of the suite reads the tree rather than the plan: two builds beside each other used to pay twice for the same answer, and a build's own gate turned red on files it never opened and left a finished pass waiting on another session. Everything downstream writes pages, comments and plan rows rather than code, so none of it runs the suite again over bytes that have not moved: the shipping step still syncs the published pages and trims the comments, and each of those is held by its own narrow proof. An explicit `/check` still runs whenever it is asked for.

**6. Ship it, then close it.** `/git-release` is the only step that writes git, and its first act is to name the files this pass wrote and put only those onto `main` — unchecked, on purpose, so they stop sitting in a checkout while the docs, the comments and the whole suite run. Its commit uses an index built from `HEAD`, so work another session has staged, left unstaged or added stays in the checkout. Both that landing and the release itself are named for the work they carry and refuse a blank name, so the history answers which commit brought what. Before the final push, its own numbered step writes the ticket's dated `Released` line, rebuilds the derived status, reads the row back and adds both files to the owned set. The release commit that follows carries only the documentation, comments, ticket transition, version and lock files this pass wrote. **Only a change somebody running the app can meet gets a version number and a tag** — the skills, the hooks, the checks and every script but one sit in the same checkout as the app and are not the app, so they land and stop there. The exception is the script that builds the release binary and packages both Windows installers: a reader runs what it made, so it takes a number like the code inside it. A release workflow holds both kinds at once and is read by which step moved: every step up to and including the one that makes the installers takes a number, and every step after the installers exist — making the release, uploading them, clearing the old ones — takes none. The four test trees run the other way: they sit inside the app's own folders and still take no number, because `#[cfg(test)]` keeps every line of them out of the binary, so a change to one packages an installer identical to the last. `/done` then moves the ticket and its row out of the live half, runs `/pm` as a separate numbered step, and reads both plan files back before it can finish.

## Every phase says how it is proved

**A phase carries at least one test box, and the box names where the test goes.** Nothing in the build asks whether a change made a test necessary, so the plan is where that question is answered — and a phase with no test box is code shipped with nothing that would have caught it going wrong.

- A test box names the claim, not the function: *a comment on its own line leaves every other block editable*, in the file it goes in.
- A fix names the test after **what went wrong**, so the same regression cannot ship twice.
- A phase whose only work is a row in `design/` asks for no test — the [design-system checks](05-design-system.md) already refuse anything those files do not list.
- What genuinely cannot be tested here — a real window, live selected text, a held pointer — is said in the phase, so a missing test is not read as an oversight.

**A plan opens with a title of its own.** The template's first line is a placeholder, and a plan that keeps it cannot be told from any other plan that keeps it — in the index, in the running order, or in a link from another plan. The title is a short form of the summary sentence one line under the not-built note, and `just check-docs` refuses a live plan still wearing the placeholder, naming the file.

**The last box in a plan is the owner's, and nothing but the owner ticks it.** It sits under its own heading at the end of the phases and holds the gesture they make to see the thing, written in what they will look at rather than as "confirm it works"; a subject with genuinely nothing to press strikes the box with that reason. `/dev` stops there, `/git-release` refuses a plan whose one open box sits anywhere else, and `just check-docs` fails on a live plan with no such heading from the day it is written — because without one a plan goes fully ticked on machine work alone, and the report that finds a plan finished then asks for it to be filed as shipped before anybody has looked at it. The same check holds the heading to its place, the last `###` inside `## Phases`, and refuses a box opening `The owner ` written outside it — a gesture left under the line every phase ends with is one nobody looks for, and it is the one open box a plan is then stopped on at the end of its last phase.

**A box struck through is neither open nor ticked.** Striking is how the tree retires a box whose work moved to another plan or changed shape: the line stays so nobody re-plans it, and it is not work left and not evidence, so `just check-docs` and `/git-release` both count past it. The strike has to be the first thing after the checkbox — one part way along a line is a box whose wording changed, and it is still open — and it has to close, since `~~moved` with no second pair draws as ordinary text with two tildes in front of it, so counting it as retired would drop a box a person can still see. **The reason the work is not happening goes on the same line, after the closing pair**, and `just check-docs` fails on a struck box with nothing after it: a struck box is out of every count that decides when a plan is finished, so that sentence is the only record the work existed. Inside the strike does not count — a bare strike is the original box text crossed out, so nothing can tell the two apart. A struck owner's box says the subject has nothing to press, never that the owner has seen what was built, so a plan carrying one stays live until they ask for it to be closed.

**A ticked box is not a build, so the running order never reads one as `Dev`.** That stage rests on a dated line somebody wrote: the `Building since` line `/dev` writes before it opens a phase, or — on the one older plan whose work landed before that line existed — a dated `Built work confirmed` line recording when that landed work was confirmed rather than inventing when it started. The tick used to stand in for both, from a time when a build looked like an untouched plan until its first box went in, and what it turned into was a design pass completing a measurement and the running order announcing a build nobody had started. The tick still needs an author, which is what `Done in the design pass.` in a phase's reason is for; `just check-docs` refuses a completed, unstruck box on a designed plan whose phase does not carry it, and a plan with either dated building line owes the note on nothing.

**Anything a pass turns up that is not the plan's own becomes its own plan.** Reading the code to write, design, build or rank one is what finds something else — a bug beside the one being fixed, a rule nothing enforces, a subject with no tests. The test is scope, not size: a find belongs to the plan in hand when a phase already in it would have to build it anyway, and otherwise it is a second file, written in the same pass and ranked with the rest. A one-line fix out of scope is still its own plan, because what makes it one is the record rather than the cost — a plan about the find bar carrying a pager fix is a diff nobody can review, and a finding left in a hand-back dies with the session.

**A hint that the work in front of a pass could be faster is a performance finding.** Repeated work, a path running more often than its result changes, a broad read where a narrow one answers, or a wait somebody would feel is enough to file a marked plan in the same pass. The gate does not stop to benchmark or fix it; measurement and the fix belong to that plan, which the Performance track keeps in tier 0.

**A plan carrying two jobs is split, the same way a blocked one is.** Each half keeps its own name and its own row, and the two point at each other. Splitting on size is otherwise nobody's call, so a plan that is really two ships half and never closes.

**A plan's file name has to be free of the shipped and turned-down half.** A plan is named after the fault it fixes, so a fault that comes back wants the name a shipped plan already carries — and that plan keeps it, being the record of the first time. `just check-plan` names both files and asks for the live one to be renamed after what is different this time, because retiring it puts the file in a folder that already holds the name, and on a checkout that reads two spellings of one name as one file the move writes over the older plan instead of refusing. A plan written as a folder of parts is named by its folder.

## Where a test goes

| What changed | Where its test lives |
|:--|:--|
| `src/**.rs` — the library | `src/tests/`, one file per subject, with the shared helpers in `mod.rs` |
| `src/app/**.rs` — the binary | `src/app/tests/`, one file per subject |
| `src/platform.rs`, `journal.rs`, `pipe.rs`, `single_instance.rs` | `src/app/tests/` as well. These sit beside the library's files and belong to the binary, so nothing in `src/tests/` can see them — the file's folder does not tell you which crate it is in, `main.rs`'s own `mod` lines do |
| `src/store/**.rs` | `src/store/tests.rs` |
| `installer/**.rs` — the Windows EXE installer | `installer/src/tests.rs`, run by `just check-installer`. It installs nothing: the plan is data, and the one test that writes drives a scratch folder and a scratch registry key and removes both |
| `src/assets/shell/*.js` — the page's script | `scripts/check-shell/`, one file per subject — the file for the part that changed, and a new one where the subject is new. `scripts/check-shell.mjs` beside it is imports, the calls in order and the report, and it is what boots the fragments in order against a stand-in page |
| A test that holds the page by a line of it | `assert_in(&html, opener, needle)` rather than `assert_contains`, wherever the page carries that line in more than one place — the opener is the line that opens the block the line has to be inside, so the test fails when that block is emptied instead of passing off a copy of the line somewhere else. `just check-shell` counts every pinned line in the string that test itself built — the joined page, the page alone, the script alone, or the exported page's minimap script — and refuses one that string holds twice. It also refuses one the string holds nowhere: each of those strings is rebuilt from the Rust that builds it, seam by seam, so a pin the Rust suite proves is there and this check cannot find is the rebuild having stopped being the string the test reads, and the rebuild is what moves. A builder it counts nothing against carries a written reason, and one with no row at all fails |
| A test that holds one rule of the stylesheet | `rule_body(css, selector)`, never a `find` or a `split` of your own. The selector is the head of the line the rule opens on, indent and all: a match counts only where it begins a line, so a rule merely *ending* with the one asked for is refused rather than answered, and a selector the stylesheet opens twice is refused naming each rule's first declaration — which is what a caller carries to say which. `rule_at` is the same find where a test is weighing two rules' places in the file rather than reading one |
| `web/preview/host.js` — the browser's own host | `scripts/check-shell/browser-host.mjs`, which boots it over a stand-in module in that same page; the embed's host has `embed-host.mjs` beside it. A new command also owes a row in the host's own table, which `just check-web-commands` refuses the build without |
| `site/*.js` and `docs/docs.js` — what draws the published pages | `scripts/check-site-boot.mjs`, which boots both entry readers and everything they import against a stand-in page, fetch and renderer module, and reads the page each one finished. The stand-in page is `scripts/check-site-boot/page.mjs` beside it, which parses markup and answers a query over what is standing, because the readers are imported as modules rather than evaluated as joined source |
| `src/assets/reading/`, `src/theme.rs`, `themes/` | the `src/tests/reading_css_*` subjects, `src/tests/theme_registry.rs`, and `just check-themes` |
| A new class, component, token or icon | No test to write — `just check-classes`, `check-tokens`, `check-icons` and `check-gallery` refuse what `design/` does not list |
| A new `scripts/*.mjs` | A self-test on made-up input at the top of its own run, proving each refusal before a real file is opened, plus a line in `just verify` — `check-verify` fails on a check the suite does not run. A `check-*` gate never puts that proof behind a flag, because the gate never passes one and a matcher that quietly stopped matching would then pass everything |
| A test that writes outside the repo | Anywhere above, and it asks `scratch_dir` for the folder rather than building a name — one helper per crate, in `src/tests/mod.rs` and `src/app/tests/mod.rs`, naming the folder after the test that asked, this run's own process id and a counter. `just check-scratch-names` refuses a fixed name, a name whose only substitution is a clock reading, and two tests asking one helper for the same word. A script under `scripts/` that builds a temporary path out of its one argument is read the same way: a fixed name handed to it is refused, followed one hop through the local `const` that bound it, and an empty name or none is the builder's own answer |

A test is named as a sentence about behavior — `a_staged_update_installs_itself_at_launch_but_only_once` — and tests the rule rather than the implementation, so a rewrite that changed nothing a reader sees does not fail it. See [Building](02-building.md#verification-suite) for what the suite runs and how to run one step of it.

## The skills

| Skill | What it does |
|:--|:--|
| `/ticket` | Writes a plan, files it under the right subject, and adds its row to the index |
| `/design` | Reads a plan against the code, fixes it, dates it, and records what was wrong |
| `/pm` | Ranks every live plan into one running order |
| `/dev` | Builds a plan's phases in order, checks each finished box by editing the plan file, stops before the gate, and stops at the owner's own box |
| `/check` | The one complete gate, run when the owner asks for it: the test reading first, then `just verify`. A failure is fixed and re-run, never explained past |
| `/test` | The owner's gate over every plan a build has landed: the plans they name, or every row at `Dev` with a box ticked, then one reading and one `just verify` for the whole batch |
| `/sync-tests` | Names the test covering each change, writes the missing ones, says what cannot be tested |
| `/sync-docs` | Makes these pages match the app, audits all authored writing as one linked wiki, takes the screenshots the pages ask for, and regenerates the crawler files |
| `/code-comments` | A quality pass over comments only — why rather than what, and no drafting history |
| `/git-release` | The only step that writes git: only this pass's named files onto `main`, then version bump, commit, tag and push when the app changed |
| `/done` | Retires a plan on the owner's word, at any stage |
| `/design-tokens` | Changes a color, value, icon or component in `design/` and runs the bundlers |
| `/shell-fragment` | Adds, splits or reorders a file in `src/assets/shell/`, where order is load-bearing |
| `/add-format` | Teaches the app another readable file type from the one table of formats |
| `/add-dependency` | Weighs a crate before it ships: what it drags in, and what the platform already offers |

The documentation pass treats the writing as a graph, not a file pile. Every authored page must be reachable from an index; the first meaningful mention of a page, ticket, skill, section, artifact or shared term links its canonical home; parent-and-child and decision relationships link both ways; folder names land on their index; citations can be reopened against the state they claim; and each shared word has one glossary definition. A check proving that link paths exist settles only one of those questions, so it cannot end the pass by itself.

Hooks back the parts of this that are worth failing rather than remembering — they print the standing rules before each message, write down the steps of the skill a message names, refuse a git write — and anything that puts the installers out — without an explicit release, refuse a build on a ticket nobody has designed, sample a build ticket's boxes after every edit and every shell command so a build that filled them as it went can be told from one that swept them at the end — both, because a session here is told to prefer a shell command for writing a file, so the edit tools alone leave the ordinary build unsampled — hold a reply to the repo's own rules about how it is written, and hold a turn whose phase's boxes never filled in while its code was landing. `just verify` self-tests every one, and it fails on a gate script nothing reaches — no settings row names it and no reached script imports it — so a forgotten line switches nothing off silently. Each record they keep belongs to one session, so a machine running two at once cannot spend the other's release, take the list the other is working, or hold it to the other's steps; a machine where no session can be identified is refused every git write rather than let through.

## Two at once, in one checkout

<!-- shared-rule: sessions-in-one-checkout -->Two sessions build in this one checkout, on tickets the running order's `Devs with` column says share no file, and neither of them writes the running order.<!-- /shared-rule --> Both work the checkout in front of them — the code, the plan folder beside it and the release all in one place, with nothing private and nothing handed over — which is what lets the boxes tick and the status turn on a screen already open rather than inside a folder nobody else can reach. Each session's own records are what keep the two apart: the release license, the step list, when the turn began, the sampled boxes and every scratch name are keyed on the session, so neither can spend the other's release, take the list the other is working, or hold it to the other's steps. Two of them stand for a turn rather than a session, and both read one hour from one place: past it a record belongs to a turn nobody ended, so a live turn is never held to a dead one's. That is also how a sentence typed into a running pass is told from a new turn — the reply gate deletes both records when a turn ends, so a record still on disk is this tree's own statement that a turn is running. A message arriving over one leaves it alone: moving the moment its turn began puts every ticket the pass filed behind its own start, which refuses a correct reply and lets a build that ticked no boxes through. A machine where no session can be identified is refused every git write rather than let through.

What tells one pair apart from another is the running order's own column. Every plan carries a written list of the files its build will change — what it will write, not the lines it read to make a claim — and the column names the three highest-ranked live plans each one shares no file with, with the total beside them. It is computed rather than written: one plan against a hundred and fifty is not a comparison anybody makes carefully twice, so a command writes every cell and a check refuses one the lists no longer give. `just devs-with <plan>` prints the whole list for one of them. The promise is that neither build lands on the other's edit, and it covers every file a build writes but three. This file is one of them and no build authors a cell in it: a stage is written in the ticket, both columns are derived from the tickets so any run reproduces them, and the authored rewrites belong to the ranking and the retirement, neither of which runs beside a build. The other two are the index and the planning glossary, which a build appends a row to when it files what it turned up beside its work. The subject orders used to be a fourth, dropped as a file every build writes; read out of the skills they have one writer and no build among them, so two plans that will both write one are now told they collide. Each subject is a file of its own with an index above them, and both the folder and the index are read that way — a plan naming the folder collides with every plan naming a subject inside it.

Each pass also leaves the other one's work alone: a ticket or a file this pass was not pointed at — half built, fully ticked, mid-round, failing the gate — stays byte for byte where it sits, not retired, not repaired, not filed about, because the session working it is already its record. Four skills say that in one sentence held to the others by the shared-rule check, and each writes its own reason after it: the gate fixes its own red and silently waits and retries on one outside the pass; the release commits only the paths this pass named before it started and ignores a file added while the checks run; the retirement leaves a ticket it was not pointed at where it sits however finished the boxes read; the build waits and retries rather than reporting a gate red outside its work. The release remains one at a time because its version and tag are shared, not because it stages the whole checkout.

What was taken back out is the private copy that once sat above this. Each session got a worktree of the app to itself, and a finished result was committed on a branch of its own and applied to the shared copy through a reservation and a recovery journal. It never converged, because the thing two sessions really collide over is the one plan folder — which is shared on purpose, and which no copy and no branch can merge: two rewrites of one ranked list are not a merge. What it did cost was ten releases in a row about the copies themselves and thirty unretired worktrees on one machine. The per-session records underneath it stayed, and they are what this one checkout runs on.

A build is watched the same way. The prompt hook writes down which designed ticket a build message named, the sampling hook samples that ticket after every edit and every shell command — every phase of it, with its boxes counted — and the reply hook reads the run of samples at the end of the turn. Sampled after the write rather than before it, because the tick that finishes a box is itself an edit: sample the other way and a tick is only ever seen by whatever edit happens to come next, so the last tick of a turn is seen by nothing. That puts every tick inside the series, which lets the reading be the rule's own sentence rather than a count — a box goes from empty to ticked when its code and its test are both in, and at no other moment, so **every rise is exactly one box and no two rises touch.** Three ways to miss it, each named in the refusal: more than one box ticked in a single edit, two ticks with none of the second box's work between them, and no tick at all while code was landing. Both halves are facts about an edit rather than about a phase, so the samples are walked once, edit by edit, and a box in one phase ticked straight after a box in another is refused exactly as two in one phase are — the boundary a build crosses once a phase is no place either half can be got past. So a phase swept at the end is refused however many edits follow the ticks, and a box whose whole work is a note in the ticket stands with no allowance of its own — the note is its own sample, so its tick has work behind it exactly like any other box's. The difference is the order, and the order is the only thing that tells the owner reading the ticket whether anything is happening.

The step list is the newest of them. A skill writes its own order as numbered headings, and the prompt hook copies that skill's steps into a list for the turn before the message is read; the reply hook then refuses to end the turn while one is un-struck, so a step cannot be skipped or reordered by a memory that drops whichever one came last. The skill file stays the only copy of its order, and a step that genuinely does not apply is struck with the reason. A message naming a skill writes that skill's steps over whatever was there, and one naming none leaves the standing list exactly where it is: the prompt hook fires when a message is submitted, which cannot tell a new turn from a sentence typed into a running pass, so deleting there took the steps out from under a pass halfway through them. The reply hook is what clears a finished turn's list, on every path a turn actually ends by, because it is the one side that knows a turn has ended — including the paths where it cannot read anything at all, since a Stop it cannot measure is still the end of a turn, and the exit it takes when it has already held once, because the host allows one hold a turn and there is nothing after it to sweep. The one turn that ends without reaching it is the one the owner stops, and its list used to hold whoever came next: so the prompt hook reads a bounded tail of the transcript it is handed, walks back over this message's own entries, and clears the standing list where the entry before them says the previous turn was interrupted. Where that tail says the turn ended on ordinary work, or cannot be read at all, the list stays exactly as it was — the hour a record is allowed still bounds it. The hook's own check opens every invocable skill and refuses one with no numbered headings; its mutation pass removes each skill's headings in turn and proves the hook then produces no list, so adding a sixteenth skill without an enforced order stops the suite. It also pins the release-status step and retirement's remove, rerank and read-back steps by name. **The list holds steps, never work** — work is a plan's boxes, which outlive the session, while a step dies with the message. The reply hook grew the same way: it refuses the phrases the rules name for themselves, including an answer walked back by a later "but" and a sentence handing a filing back to the owner where nothing was filed, strips quoted material first so a reply naming a rule is not refused for the words it is quoting, and requires a finished pass to echo the owner's whole message rather than only its skill name, argument or one line — measured as the whole reply against the whole message, since read a block at a time a message of two lines came back as two blocks that each looked like a piece of it, and the refusal then asked for less than the owner wrote. The host permits one hold in a turn, so every hold over a message naming a skill carries that whole message after its refusal; the reply written after the hold reads the exact words it owes instead of trying to remember them after the second stop exits.
