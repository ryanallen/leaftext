# Architecture

> Leaftext is a Rust desktop app using tao for windowing and wry for WebView. The Markdown pipeline, the IPC bridge, the vault registry, and the git integration are all covered here.

Leaftext is a single Rust binary that embeds a WebView (via `wry`) inside a native window (via `tao`). The Markdown rendering pipeline runs on the Rust side; the result is injected into the WebView as HTML. All user interaction — opening files, navigating history, adjusting settings — flows through a typed IPC bridge between JavaScript running in the WebView and the Rust host.

The same renderer also builds for the browser. The window, the WebView, the file dialog, the watcher and SQLite are optional dependencies the binary asks for by name, so the library alone compiles for `wasm32` — see [The browser modules](#the-browser-modules).

## Core crates

| Crate                   | Role                                                 |
| ----------------------- | ---------------------------------------------------- |
| `tao`                   | Native windowing and event loop. Optional: the `desktop` feature |
| `wry`                   | WebView embedding (WKWebView / WebView2). Optional: the `desktop` feature. Its `transparent` feature is named: on macOS the call that turns the WebView's own background off is compiled out without it, and the app's shadow band needs what is behind the window to show through |
| `pulldown-cmark`        | CommonMark + GFM Markdown parser                     |
| `syntect` + `two-face`  | Syntax highlighting for code blocks. Optional: the `highlight` feature, so a browser module can be built without them |
| `ammonia`               | HTML sanitization (allowlist-based)                  |
| `rusqlite` (bundled)    | SQLite for the [vault](../01-features/03-library.md#vaults) registry. Optional: the `desktop` feature |
| `rfd`                   | Native file dialogs. Optional: the `desktop` feature  |
| `serde` / `serde_json`  | IPC message serialization                            |
| `notify-debouncer-mini` | Filesystem watcher for live reload and the [library pane](../01-features/03-library.md#live-updates). Optional: the `desktop` feature |
| `blake3`                | Content hashing: re-checking a staged installer before it runs |
| `flate2`                | Deflate for the PNG encoder in `src/png.rs`. Already in the tree under `syntect`, so it costs a line rather than a crate |
| `roxmltree`             | Read-only XML DOM parsing for TEI and other XML      |
| `yaml-rust2`            | YAML parsing for the [data renderer](../01-features/01-rendering.md#data-files-json-and-yaml). JSON needs no crate — `src/data.rs` reads it directly, which is what keeps key order and exact byte ranges |
| `mail-parser`           | MIME parsing for the [email renderer](../01-features/01-rendering.md#email-eml): multipart trees, base64/quoted-printable bodies, encoded-word headers, per-part charsets |
| `windows-sys` (Windows) | Win32 calls: single-instance guard, clipboard, Recycle Bin, the WinHTTP update download, waiting for the app to exit before an update installs. The [EXE installer](#the-windows-exe-installer) takes it again with a shorter list of its own, plus COM for the Start Menu entry |
| `webview2-com` + `windows` (Windows) | The [PDF the page export writes](../01-features/02-navigation.md#export-the-page): WebView2's own `PrintToPdf` renders the page straight to a file, so no print panel is ever raised. Both already compile in through `wry`, so the lines buy the name to call that method by rather than any code |
| `objc2` + `objc2-app-kit` + `objc2-foundation` (macOS) | The same export on a Mac: the web view's print operation with both panels switched off, the sheet the page measured as the paper, and the chosen path set as where the job saves to. All three already compile in through `wry`, at the features it already asks for |

The list is deliberately short. Clipboard, Recycle Bin, per-user data paths, update downloads, and [git](../01-features/03-library.md#github-sync) are all done against the platform rather than through a crate — see [Dependencies](../../AGENTS.md) for the standing policy, and `src/platform.rs` for where the native code lives.

Features are trimmed for the same reason. `syntect` is taken with `default-features = false` and only `parsing` and `html`: its syntax definitions come from `two-face`'s binary dumps, so its own bundled syntax and theme dumps are dead weight, and its `yaml-load` feature — which reads `.sublime-syntax` YAML and was the only thing pulling in the unmaintained `yaml-rust` — is not needed at all. `yaml-rust2` is likewise taken without its `encoding` feature, since files reach it as decoded Rust strings.

The regex engine behind the highlighter is chosen by feature rather than pinned: the desktop takes `regex-onig`, which is oniguruma, a C library; a browser module takes syntect's pure-Rust `regex-fancy`, because oniguruma has no `wasm32` build. Both read the same syntax dumps, and a test pins the markup they have to agree on.

## Source files

Leaftext's Rust source is split by concern. Where a concern grew past one file it became a directory whose `mod.rs` holds the shared vocabulary and the pipeline that orders the stages, with one sibling file per stage. Both crate roots live in `src/` — `lib.rs` for the library, `main.rs` for the binary — so the binary's modules sit under `src/app/` to keep the two namespaces apart.

- **`src/main.rs`** — Entry point. Builds the window and the WebView2 instance, registers the custom protocol handlers, and runs the startup sequence that assembles the event loop's state. The window is built at `STARTUP_INNER_SIZE` — 256 by 256, holding the [startup card](../01-features/05-settings.md#window-size) — and asks for neither the saved size, the saved maximized state nor `MIN_INNER_SIZE`: all three are applied together when the page says it has drawn, since the limit is larger than the launch window and would clamp it away at the builder. It tunes WebView2 with a trimmed browser-argument set (site isolation and background networking off, GPU and the renderer kept hot) to reduce the process/background footprint of a single-window offline reader. Three argument forms open no window at all: the detached update applier, `--squeeze-png <in.bmp> <out.png> [--palette]`, which is how `just squeeze-png` reaches the encoder in `src/png.rs`, and `--dump-css`, which prints the compiled stylesheet so `just bundle-gallery` can paint the [gallery page](https://leaftext.com/gallery.html) with the same CSS the app paints itself with.
- **`src/app/`** — The binary's guts. `event_loop.rs` holds `AppCtx` (the state the loop owns between events) and the loop itself: one arm per thing the window, the page or the watcher can report. Around it, `events.rs` (`IpcCommand` — the page's whole vocabulary — plus `UserEvent` for the app's own signals, the IPC bridge, and `off_loop`, the one way work is handed to a worker thread), `workspace.rs` (`Workspace` and `Tab` — a new tab inherits the [source view](../01-features/07-editing.md#code-view) from the one you were in), `history.rs` (back/forward and the scroll position each entry remembers), `watch.rs` (the `FileWatch` live-reload watcher), `vaults.rs` (the vault switcher, the folder reads, and the corpus's lifecycle — including `record_or_refresh_corpus_path`, the one door every change to a document takes, whether it was saved here or written by something else: it re-reads the file straight away against finished text, and while the read that fills that text is still running it keeps the path instead, because the slice that replaces the preview would throw the change away and a later slice would carry the file back as it was before the save. The last slice replays every kept path before the map, the completion menu and the final search are taken from the finished vault), `vault_search.rs` (the one search thread, and `WorkGeneration` — the counter a worker reads between documents so a keystroke the field has moved past stops rather than finishing, held once for the search and once for the vault read, never shared, since one counter would have each canceling the other; the vault read's number rides every slice it hands over, because a vault left and come straight back to is the same folder again, so the root a slice names cannot tell an abandoned read's tail from the live read's), `vault_git.rs` (the [GitHub panel](../01-features/03-library.md#github-sync)'s jobs, each on its own thread, and the tag a failed one carries so the page can point at the fix above it), `vault_remote.rs` (the clock that asks a vault whose files live on a service what has moved, which vaults are worth asking, and the resting a source that keeps refusing earns — three refusals and it stops until somebody presses Refresh), `vault_auth.rs` (signing one in: the consent page opens in the person's own browser and the answer comes back to a listener on a loopback port the OS picked, served once and then given up), `eval_ask.rs` (the `eval` ask's answer: the caller's line goes into a `try` with a numbered mark declared after it, and a second call reads that mark back, so a script that threw comes back with the engine's own message and a script the page never read comes back saying so rather than as the `null` all three used to share), `pipe_asks.rs` (the rest of the ask pipe's arms, one function each — what is open, a document's source, a splice spliced as one undo step, a task toggled, a save, a PDF and a picture — moved out of the loop the way `eval_ask.rs` was before them, so each arm there is the pattern and the line that calls one; the arm that answers a document's source waits for the render and refuses when it failed, carrying the sentence the reader is already shown, because the tab is rolled back on a failed open and an answer composed after it would describe whatever document the rollback left in front; the two that end the app stay in the loop, because they reach `shut_down` and the loop's own `control_flow`), `gesture_ask.rs` (the `gesture` ask: a pointer gesture — wheel, click, right-click, move, drag, hold, release — played into the page over the web view's own developer protocol, which needs no cursor, no focus and no place on screen and so reaches a copy standing off every monitor; the ask carries the picture's own pixels and this divides by the window's scale, a drag is paced on a thread of its own and lands back on the loop one `PipeGestureStep` per step so the loop is never held for the walk, and `type`/`key` are refused with `eval` named, since every shortcut already goes through it), `file_cmds.rs` (what the page's file and favorite commands do, one function each — open, new, paste, reveal, copy, favorite, rename, delete, put back, properties — beside `fileops.rs` rather than inside it, since that file already holds the work these call and is long enough), `window_cmds.rs` (the window's own commands, and the arithmetic under the shadow band's resize: Windows hands a whole gesture to the platform on the press and a Mac is refused that call, so the host holds the window as it stood and sets it from every move. `finish_startup` is here too: the one growth a launch gets, asked for by `startupReady` or by a four-second deadline behind it, applying the smallest window first, then the reader's size, then their maximized state — that order because setting the limit last made Windows hand back a window filling the screen that the platform no longer called maximized. `WindowClose` is not here — it reaches `shut_down` and the loop's `control_flow`), `editing_cmds.rs`, `code_intel.rs` (gathers what a [typing help](../01-features/07-editing.md#typing-help) ask needs — the corpus or the document's folder, the edit buffer — and computes the answer on a worker), `render.rs` (`Reader`: the window, the page, the tabs and the recents that every render needs, bundled so a render is one call, the per-tab render cache, and the one look at the disk that brings a tab's clean edit buffer back into step with its file when a reader arrives at that tab — the live reload only ever refreshes the tab in front, so without it a document edited once goes on showing what it held when it was left. A render hands back whether the document opened, since this is the only place that finds out; the window itself needs no answer and drops it, and the ask pipe is the one caller that reads it), `glossary.rs`, `links.rs` (what a clicked href means), `picture_clipboard.rs` (a picture on the system clipboard as pixels: the desktop page is not a secure context, so it has neither `navigator.clipboard` nor `ClipboardItem`, and what crosses from it is the PNG its own canvas wrote — one encoder for every kind of picture the reading view draws, rather than a decoder here that would fail according to the picture's source format. Both helpers read from a path, so the bytes land in a scratch file of this process's own, created rather than opened and removed whether the helper worked or failed), `link_preview.rs` (the render behind the [card a hovered link raises](../01-features/02-navigation.md#link-hints): the local document that link names, drawn through the same routing table a tab draws through, so each format reaches its own renderer rather than every file being read as Markdown. How much of the file is read is an exhaustive match on the format, because the answer differs by parser — a Markdown note reads its first 256 KB, wide enough to carry every section a reader can rest on, because the page is what lifts the one the address names out of the answer; an [XML](../01-features/01-rendering.md#xml), [JSON, YAML](../01-features/01-rendering.md#data-files-json-and-yaml) or [email](../01-features/01-rendering.md#email-eml) file is read whole, since a cut one is a parse error rather than a smaller document, and one past a megabyte answers nothing rather than spending a fifth of a second of render on the event loop. What the card is handed is not that whole answer: the page parses it once, takes the section the address names or the file's own opening where it names none, and serializes whole top-level blocks up to a 4 KB ceiling — so a long document is laid out as the opening the 176-pixel card can show rather than entire, and a first block past the ceiling is kept whole so nothing is drawn half closed. The render is asked for through a host that draws no Previous/Next waiting strip, since the card walks no folder and a strip in it would pulse for as long as the card is up. The answer is kept per thread against the file's own modified time, so pointing along a list of links costs one render each and a page edited under the pointer draws again; the cache drops its oldest entry past a fixed count rather than holding every file rested on for the session. A link that is not a readable local document, or one whose file has been deleted or renamed, answers nothing and the page settles the card without it), `fileops.rs`, and `update_flow.rs`.
- **`src/app/export_cover.rs`** — The native page-color sheet above the web view while an export render rearranges it.
- **`src/lib.rs`** — Core document rendering and app-state helpers. Contains `render_markdown_document()` (which orchestrates the Markdown pipeline in `markdown/`), document loading, glossary auto-linking, recent-files and settings persistence, and `app_shell_html()`, which assembles the WebView page from the shell markup in `src/assets/` (see below) and fills in the five things only the host knows: the front-end, the theme bootstrap, the theme picker's cards, and two asset URLs. The front-end is the one of those five that differs by host, which is why `app_shell_page_for_host()` takes it as an argument: a browser host gets the deferred tag `front_end_tag_html()` writes, and the desktop gets `desktop_front_end_loader_html()` — the loader in `src/assets/desktop-front-end-loader.js`, inline, naming that same joined `app.js`.
- **`src/host.rs`** — `LeafHost`: what the renderer asks the machine it is running on for, so the same render works where there is no machine to ask. Two halves. Four reads it cannot get from the document's own text — the vault's field types, the repository a `#123` resolves against, an image's own pixel size, and the nearest glossary — plus resolving a path and taking a line of log; and the commands the page sends: open, save, splice, follow a link, search, draw the map, find an asset, fetch the highlighter, read and write settings, the Previous/Next strip, and the two questions a picture beside the document turns on — whether the host serves the open document's own folder, and where it serves the document's neighbors from. The desktop serves that folder itself, over `leaf-image://`, because its page resolves a relative path against nothing. A browser does not, and then the second question splits the two browsers apart: a document inside somebody else's product is fetched from beside its own pictures, so it answers nothing and the address as written is left alone, while a published site answers with the folder it serves every document out of and the renderer joins that with the document's own folder. Every method has a default, so a host implements only what it can answer, and a host that answers none of the four renders the document without those decorations rather than failing. `DesktopHost` is this machine — the running app hands it the three things the library cannot reach on its own: where the settings file is, the vault's text, and a way to hand a link to the OS. It also carries one switch of its own, which the [hover card](../01-features/02-navigation.md#link-hints) is the only caller to set: draw no Previous/Next waiting strip, because a waiting state is a promise and nothing is coming for a card that walks no folder. `BareHost` answers nothing, which is what proves the interface is optional rather than load-bearing.
- **`src/format.rs`** — `DocumentFormat` and the single table of readable formats and their extensions. Everything that has to know what counts as a document asks this one: the Open dialog's filters, drag and drop, whether a clicked link opens in the reading view or goes to the OS, the [pager](../01-features/02-navigation.md#pager)'s page list, the [library](../01-features/03-library.md)'s indexable set, and the render router's choice of pipeline. `for_path()` answers whether a file can be opened at all (`None` if not); `from_path()` answers which renderer to use, falling back to Markdown so an extension-less `README` still opens. Adding a format is one arm here — the matches on it are exhaustive on purpose, so the compiler names every site that must account for it. Public, re-exported at the crate root.
- **`src/html.rs`** — Complete HTML documents: the file-name heading and the shared rendered-HTML sanitizer, with no reading-view source ranges.
- **`src/text.rs`** — Plain text documents: the file-name heading and the whole file as one preformatted block, escaped and otherwise untouched. Nothing is parsed, because the app was never told what shape the file holds — a banner, an indented list and a hand-wrapped paragraph all arrive as they were saved rather than reflowed into prose, which is what reading one as Markdown did to them. The block carries no source range and the document answers an empty block source map, so the source view is its editing path: a range covering the whole file would draw the source view a second time inside the reading view.
- **`src/ini.rs`** — INI configuration files: the reader and the dialect it reads, which is written down at the top of the file because there is no INI standard to conform to. `parse_ini()` answers `src/data.rs`'s own `DataNode` tree, so the page is the one a JSON file already draws — a section is a heading and its scalar keys are the label-and-value list under it — and `render_ini_document()` asks that renderer for keys drawn as they were typed rather than sentence-cased, since `font_size` is a name somebody chose. Every value carries the exact byte range of its own text, which is what the reading view splices when the value is typed into. `pub(crate)` and re-exported at the crate root.
- **`src/scripts.rs`** — Generators for the small JS snippets the host injects to drive the WebView: initial/document/workspace state, navigation, scroll anchoring (`ScrollAnchor`), the glossary sheet, and error state. Each returns a `String` of `window.leaf*(...)` calls that the event loop hands to `webview.evaluate_script()`. The state is written out as a JavaScript value. Handing it over as `JSON.parse("…")` instead was tried and is slower here: that trick wins on dense object structure and loses on long strings, because the text is scanned and unescaped once as a JS string before the JSON reader sees it — and a document payload is mostly two very large strings, the rendered HTML and the source.
- **`src/pager.rs`** — The Previous/Next pager: walks the document's folder tree in reading order (`document_pager_html()`, `PagerEntry`, `pager_label()`) and builds the pager HTML plus the async `pager_loaded_script()` hand-off.
- **`src/xml.rs`** — The XML front door and the generic renderer. `render_xml_document()` / `render_xml_body()` / `xml_block_source_map()` parse once (`parse_xml()`, doctypes allowed) and route by content: a `<TEI>` root or a `<teiHeader>` goes to `src/tei.rs`, anything else renders here. The generic renderer has no schema to work from, so it reads the shape of the tree — an element holding only text becomes a label/value field, runs of them share one field list, repeated flat records become a table, an element holding other elements becomes a section headed by its `<title>`/`<name>` child or its humanized tag name, and mixed content becomes a paragraph. Blocks that come from exactly one element carry that element's byte range, so [inline editing](../01-features/07-editing.md#inline-editing-the-reading-view) anchors the same way TEI's does. `pub(crate)` and re-exported at the crate root.
- **`src/tei.rs`** — The TEI XML renderer, reached through `src/xml.rs`: converts an 84000-style TEI document into the same HTML the Markdown pipeline produces (`render_tei_inner()`, `tei_render_div()` / `tei_render_node()`, `TeiCtx`, `tei_slugify()`). Stamps each editable block with inline `data-src-*` source byte ranges (from `roxmltree`'s `Node::range()`), so [inline editing](../01-features/07-editing.md#inline-editing-the-reading-view) works for XML too. `pub(crate)` and re-exported at the crate root.
- **`src/data.rs`** — The [JSON and YAML](../01-features/01-rendering.md#data-files-json-and-yaml) front door and their shared renderer. Both formats parse into one ordered `DataNode` tree (`parse_json()`, `parse_yaml()`) which `render_data_document()` renders through the same shape rules and label helpers `src/xml.rs` uses, so a sitemap and the JSON beside it read alike. The JSON reader is hand-written rather than a crate: it keeps key order, shows numbers as the file wrote them, tolerates comments and trailing commas, and — because it knows exactly where each value begins and ends — gives every node an exact byte range. The YAML reader drives `yaml-rust2`'s event stream, resolving `*alias` references and splicing `<<:` merge keys, converting the scanner's *character* markers to byte offsets as it goes. One cursor does that conversion and it walks both ways: markers are not strictly ordered, because the scanner reports a block mapping back at the indentation of the key that opens it, so the cursor takes those few characters off the place it already has rather than counting from the top of the file again. Counting again instead cost a nested megabyte 5.2 billion character steps of a 1.1 million step job. `parse_yaml_counting_walk()` is the same parse handing back the number of characters walked beside the tree, which is what a test holds that bound with — the same figure on every machine, where a wall-clock reading is not. A block is stamped with `data-src-*` only where its range is provable (`scalar_span()` checks a scalar's source text against its parsed value), because the reading view splices that range verbatim. `pub(crate)` and re-exported at the crate root.
- **`src/eml.rs`** — The [email](../01-features/01-rendering.md#email-eml) renderer for `.eml` (and `.mht`/`.mhtml`, the same MIME envelope). `render_eml_document()` parses the message with `mail-parser`, then builds the page: the subject as heading, a From/To/Cc/Date field list with `mailto:` links, the HTML body through the same `ammonia` policy Markdown's raw HTML crosses (plus the `cid:` scheme, kept only long enough for the pass after sanitizing to swap each inline-image reference for a `data:` image built from the message's own parts), a linkified-paragraph fallback for plain-text bodies, and an attachment list. Nothing reaches the network. A part whose drawn words can be written back to the file byte for byte carries a source range and is typed on in the page; a body or a header line the transfer coding rewrote carries none, and the code view edits the raw message. `pub(crate)` and re-exported at the crate root.
- **`src/minimap.rs`** — The document minimap model: `build_minimap_model()` / `build_minimap_model_from_html()` and the `DocumentMinimap` / `MinimapSpan` types that classify each line run (heading, paragraph, list, blockquote, code fence) for the scrollable overview. Only `line_count` is serialized to the page — the [rail](../01-features/04-minimap.md#how-it-works) draws itself from a clone of the real rendering, so the spans would be megabytes of payload nothing reads. `pub(crate)` internals with the public model types re-exported at the crate root.
- **`src/editing.rs`** — The [editing](../01-features/07-editing.md) model: `EditableDocument` (the per-tab source buffer with dirty tracking, a save version counter, `replace_range()` splices for inline edits, `toggle_task()` for checkbox flips, and the bounded [undo](../01-features/07-editing.md#undo) stack), `block_source_map()` — a `pulldown-cmark` `into_offset_iter()` pass mapping each top-level Markdown block to its exact source byte range — and `task_marker_offsets()` for the interactive checkboxes. These source maps are what [inline editing](../01-features/07-editing.md#inline-editing-the-reading-view) anchors its splices to. **The list is in the order the page draws the blocks, not the order the file was written**, because the page pairs the two by position and has no other way to line them up: a [footnote](../01-features/01-rendering.md#footnotes) definition is written mid-file and drawn at the foot, so its span moves to the end by the same rule in `src/markdown/footnotes.rs` that moves its events. Anything else that reorders what is drawn owes its spans the same move, and the page refuses the whole mapping — stamping nothing — when a block's kind cannot be the element it landed on. Public types re-exported at the crate root.
- **`src/encoding.rs`** — What a file's bytes mean as text, and the one way a document is read from or written to disk (`read_source()` / `write_source()`). `decode_source()` reads the byte order mark to pick a decoder — UTF-8, UTF-16 or UTF-32, either byte order — falls back to Windows-1252 for unmarked bytes that are not valid UTF-8, and refuses anything holding a zero byte as not being text. `encode_source()` writes the file back the way it was read, so saving never re-spells a document. `read_source_head()` reads only the first N bytes for a caller that wants what is at the top of a file across a folder of them, dropping the bytes of a character the cut split rather than decoding them as something else. A leading mark is taken off the text and remembered on the `SourceSpelling` instead of left in it, because a `U+FEFF` at offset zero makes `pulldown-cmark` read the first line as a paragraph, stops `---` opening frontmatter, and makes `serde_json` refuse the document. All `std` — no encoding crate. Public and re-exported at the crate root. See [file encodings](../01-features/01-rendering.md#file-encodings).
- **`src/assets.rs`** — Bundled-asset serving and icon processing: the `include_bytes!` Mermaid/KaTeX runtimes, the Monaco editor behind the [code view](../01-features/07-editing.md#editing-the-source), and the PixiJS + d3-force bundles that power the [Graph view](../01-features/03-library.md#graph), `bundled_asset_response()` for the `leaf-asset://` scheme, the toolbar/brand SVG constants, `normalize_svg_icon_colors()` (rewrites literal icon colors to `currentColor`), and `SITE_MINIMAP_JS` — `site/minimap.js`, the browser [minimap](../01-features/04-minimap.md#on-an-exported-page) both published sites run, compiled in so an [exported page](../01-features/02-navigation.md#export-the-page) can carry its own copy and the rail's arithmetic has one source in the tree. Not to be confused with the `src/assets/` directory it embeds. `pub(crate)` (plus the public `bundled_asset_response` / `BundledAsset` / `LOCAL_ASSET_PROTOCOL`), re-exported at the crate root.
- **`src/markdown/`** — The Markdown rendering pipeline. `mod.rs` runs the stages in order; `events.rs` transforms the event stream between parse and render, `headings.rs` does heading anchors and document titles, `github.rs` the GitHub extras (autolinks, issue/PR references, emoji, alerts, repo context), `footnotes.rs`, `code.rs` the `syntect` highlighting — including `SYNTAX_STYLE_RULES`, the table of every `.syn-` rule the stylesheet has, which is what lets a highlighted token be one flat element carrying only the classes some rule needs — `images.rs` image URL resolution, `image_size.rs` the pixel size read out of each local image's own header and stamped onto the tag — after the sanitizer, since the numbers are the app's own — so the page reserves the right space before the picture decodes, `image_protocol.rs` the `local_image_protocol_response()` handler for the `leaf-image://` custom scheme, and `paths.rs` percent-coding. Two files carry the sanitizer: `rawhtml.rs` decides what raw HTML inside Markdown may keep and configures `ammonia`, and `htmlparse.rs` does the tag and attribute scanning underneath it — no policy, and no dependency on anything else in the crate. Items are `pub(crate)` and re-exported at the crate root.
- **`src/theme.rs`** — The theme system. The semantic token contract (`LEAF_SEMANTIC_TOKEN_CONTRACT`), the `ThemeSource` / `ThemeFile` types, and the CSS compiler: `theme_sources()` (which parses the bundled `src/assets/themes.md` once via `parse_theme_markdown()` and leaks it to `&'static`), `compiled_theme_css()`, `theme_source_token_value()`, `assert_theme_sources_cover_contract()`, and `reading_mode_css()` — which prepends the compiled token blocks to the stylesheet in `src/assets/reading.css`, so every `var(--lt-*)` in it resolves. Palettes are data, not code, and so is the stylesheet: neither lives in Rust tables. Its items are `pub(crate)` and re-exported at the crate root. See [theming](04-theming.md).
- **`src/store/`** — The [vault](../01-features/03-library.md#vaults) registry, and the two parsers that go with it. `vaults.rs` holds the rows (add, rename, re-root, remove, and `vault_containing()`, which answers which vault holds a path — innermost wins); `db.rs` opens `manifest.db` and migrates its schema. `frontmatter.rs` and `links.rs` take text and give back fields and link targets; neither ever needed a table, which is why they outlived the one they were written for. `frontmatter.rs` also holds the one read of a document's leading block (`document_fields`) and the readers over it — `aliases_from` for the [other names](../01-features/03-library.md#other-names) a note answers to, capped at 32 aliases and deduped by the key names match on — so something wanting two keys does not parse the block twice. A field carries its [type](../01-features/01-rendering.md#frontmatter), the case its key was written in, and the byte range of both key and value, so anything pointing at one field in the source has the offsets already rather than scanning the block a second time; `scalar_type` is the one place a type is worked out. A line that is not a field — nesting, a repeated key — is refused and recorded rather than turned into a field nobody typed. The same file holds the write side: `set_field`, `set_list_field`, `rename_field` and `remove_field` each return one splice over the bytes the parser already located, never a re-serialize of the block, because comments, blank lines and refused lines are not fields and writing the block back would drop them. A value is quoted only where reading it back needs it, and one that arrived quoted keeps them; a list goes back in the form the file wrote it in; taking the last field takes the fences with it. `obsidian_types.rs` is the two places a type can be overridden: a vault's own `.obsidian/types.json`, found by walking up the document's ancestors for the `.obsidian` folder the way the renderer already walks up for a `.git`, and a `leaftext-types` line in the note. Which folder holds that file is remembered per folder — the walk is eight disk checks and it ran on every open, which cost a fifth of a whole render. A [web address](../01-features/03-library.md#web-addresses) is one of those targets (`DocLink::target_url`, deduped by `normalize_url`, named by `url_host_label`), and bare URLs are found by `markdown::plain_text_urls` — the same finder the renderer linkifies with, so a link the reader can click is a link the graph draws. `mod.rs` holds the shared shapes (`FileTreeNode`, `DocumentGraph`, `GraphEdge` — directed, with `mutual` for a pair that links both ways — `SearchHit`) and the path helpers. The crate's only public module. A vault row also carries where its files came from and, where it is signed in, whose account — never the token, which is the machine's own credential store's; `remote_files.rs` maps a source's own id to the file it became on this machine and the version stamp it arrived with, which is what makes a rename upstream move one row rather than leave a ghost beside it.
- **`src/remote/`** — A vault whose files live on a service the machine has no client for. `mod.rs` holds the trait every source answers — list a folder, fetch one document, push one back, and say what has moved since a token — plus the pipeline that fills the copy on this machine and the one that pushes a save back; `mirror.rs` owns that copy, under the data folder and keyed on the vault's row id; `folder.rs` is a source that is just another folder on this disk, which is what proves the copy with nothing that can rate-limit. Only the formats `src/format.rs` lists come down, and a name a source gives is refused unless it is one path component — an entry called `../elsewhere` would otherwise write outside the folder the app owns. Nothing here is a crawl: one folder the person picked, and what is under it. The trait and the copy are the library's, so a source that talks to a network is the binary's until somebody decides otherwise — the request and the credential store are `src/platform.rs`'s.
- **`src/known_folders.rs`** — Where the desktop sync clients keep their folders, so a [cloud already on this machine](../01-features/03-library.md#your-cloud-is-already-a-folder) becomes a vault with no account and no token. Dropbox, OneDrive, iCloud Drive, Box, Nextcloud and Google Drive each put a real folder on the disk and keep it in step themselves, so the vault is a plain folder vault and the client is the sync. `cloud_folders()` reads named locations only — a handful of `is_dir` checks, plus the one small file a client writes its own location into when it has been moved (`info.json`, `nextcloud.cfg`, and the environment variables OneDrive sets for itself) — so nothing walks a tree. `cloud_folders_to_register()` says which of them is not a vault yet, and `path_is_in_cloud_folder()` answers whether a path saves through one, both spelling a path one way first so a trailing slash or the other slash cannot make one folder look like two. A recorded location is still checked before it is used: on the machine this was built for `%OneDrive%` is set, names a folder that was never created, and has no account behind it. Google Drive is found on macOS only — there it mounts under the file provider folder with the account in its name, and on Windows it mounts as a drive letter the person picks with nothing recording which, so guessing one would hand somebody else's disk over as a vault. `CloudRoots` is passed in rather than read inside each check, so a test can point the whole table at a temp folder instead of passing by doing nothing on a machine with none of these clients installed. Public and re-exported at the crate root.
- **`src/folder_tree.rs`** — The [library pane](../01-features/03-library.md#file-tree)'s files. `read_folder_listing(root, path)` returns one directory's immediate children plus the trail down to it; the top is the active vault's folder, or the drive roots. Nothing below is touched, so nothing is walked that nobody opened.
- **`src/vault_corpus.rs`** — The vault's text, in memory. One read serves both things that must see inside every document: `graph()` builds the [link map](../01-features/03-library.md#graph) and `search()` answers the [search box](../01-features/03-library.md#search) — as `search_until()` when the caller can say the query has been overtaken, which is how a keystroke abandons the one before it. A term is matched against the file's own text, never a lowercased copy of it: an offset borrowed across that copy pointed at the wrong window and could land mid-character. There is no index behind it, so the files are the only copy of the truth and this is a cache the watcher patches a file at a time (`refresh()`, which reports whether the patch changed anything — the answer decides whether a map on screen is redrawn). Dropped on a vault switch and on quit; capped at 25,000 documents and 32 MB of held text, whichever is reached first, with the smallest documents read first so the budget buys as many of them as it can. The read hands its documents over in slices of 50 as it opens them (`read_in_slices()`, which the one-piece `read()` is written in terms of), so a query parked on it is answered several times a second while the rest of the vault is still being opened. Those sorted slices wait on the whole folder walk, because the smallest-first order the budget depends on needs every path listed before anything is opened — so one preview goes out ahead of them, up to 50 documents in the order the walk met them, bounded by the same 32 MB ceiling off the directory sizes the walk had already read and handed over at the first folder that turned any up or the moment either bound is reached. Every slice says whether it replaces what it lands on or grows it: the preview replaces, and so does the first sorted slice, which is what drops the preview rather than holding a document twice or keeping one the final limits left out. Nothing keeps the preview's documents, so the sorted read opens those same files a second time, and that is a decision somebody measured: the second open lands seconds after the first on files the operating system still holds, costing 1.8 ms against 21.4 ms cold for a batch of 50, inside a cold read of 1,732 ms — about a thousandth of the wait, where keeping the batch instead would stand up to 32 MB of decoded text beside a corpus allowed the same. The slices after that grow, and the map and the completion menu still wait for the last. `read_in_slices()` takes the same `overtaken` closure `search_until()` does, asked between documents and at each folder of the walk, so leaving a vault stops its read instead of paying for a folder nobody is in; a stopped read breaks its loop rather than returning, because the final slice it then delivers is the only thing that frees the next vault to be read, and it marks its picture partial the way either cap does. `folder_holds_generated_files()` is what that walk stops at — a folder carrying a `CACHEDIR.TAG` with the standard signature, or one of eleven names a build tool picks — and `path_holds_generated_files()` is the same rule asked of a path that changed, which is how `src/app/watch.rs` refuses those folders' events at the boundary git's own bookkeeping is refused at. One rule for both, because a walk and a watcher answering differently would leave a vault reporting a folder it is still paying for; `src/git.rs`'s nested-repository scan asks it too, so there is one list rather than three. The walk hands back what it left out beside what it found, and that rides every slice to the line above the search rows. A document carries its [aliases](../01-features/03-library.md#other-names) alongside its label, and they go into the name index in a second pass so a real file name always beats a preferred one; search scores the best of the two through one `name_score`. `build_graph()` and `narrow()` are free functions rather than methods, because a map of one document is built from the same two and differs only in which documents it gathers.
- **`src/doc_graph.rs`** — The [link map](../01-features/03-library.md#graph) around one document, for a document no vault holds. `document_graph(seed, request)` reads that document, the documents in its folder (one level), and whatever it links to — so the work is bounded by the document's link count rather than by the disk under it. Nothing is cached: the vault's text is held because reading it costs thousands of files, and this costs one folder. This is what replaced the old "fall back to whatever folder the pane is showing", where opening the map at `C:\` walked the drive; and it is why the graph needs no vault, which it wrongly did in v0.1.407.
- **`src/query.rs`** — One filter syntax, parsed once and asked of anything. `#work status:open due:<friday -draft` means the same thing wherever it is typed, so the [search box](../01-features/03-library.md#filtering) and the task views share one parser instead of two that nearly agree. `Query::parse()` builds the tree and `Candidate` is the handful of questions a caller answers about one thing being filtered — nothing here knows what a document is, which is what lets a vault document and a task be filtered by the same string. **The parser is total**: a search box holds half a query nearly all the time, so an unclosed quote, an unmatched bracket and a trailing `OR` all mean something rather than raising an error where results should be. A caller that cannot answer says `FieldAnswer::Unknown` and the condition that asked matches nothing, because the alternative is a caller guessing, which is how a filter comes to lie about what it filtered. `Needle` lowercases each piece of text once when the query is parsed and picks the byte it will skip to — the rarest letter in it, since 'm' in "dharma" turns up half as often as 'd' does — so a keystroke over a vault pays for that once instead of per file. `describe()` is what the line under the box reads the filter back with. Public and re-exported at the crate root.
- **`src/code_intel.rs`** — What the code view's [typing help](../01-features/07-editing.md#typing-help) knows — Monaco raises the IntelliSense widgets, this answers them: note lists for `[[` completion (`corpus_note_items()` / `folder_note_items()`), a document's headings with the renderer's own anchors (`document_headings()` runs the same pipeline that stamps heading ids, so a completed `](#anchor)` always lands), note lookup and hover previews (`find_note()`, `read_folder_note()`, `note_preview()`), and the broken-link check (`lint_links()`, built on the same `document_links()` scan the graph draws from — `DocLink::span` places each link, and the markers come back in the editor's own 1-based UTF-16 coordinates). Answers come from the vault's corpus when it holds the document, or the document's own folder otherwise — never more of the disk than the graph reads. The folder arm takes names off the directory listing and the [other names](../01-features/03-library.md#other-names) off the top 8 KB of each file, capped at the 500 a loose document's map already reads. `NoteNames` carries who claims each name, so the check can say a name two notes answer to opens the file rather than only that a name is unknown. Public functions re-exported at the crate root.
- **`src/git.rs`** — [GitHub sync](../01-features/03-library.md#github-sync). Shells out to the machine's own `git` rather than speaking the protocol, for the same reason `src/platform.rs` shells out to `msiexec`: the user's git already knows who they are and how to sign in, and a crate would ship a second copy of all of it. `git_tooling()` reports what is installed, `inspect_vault_repo()` reads a folder's standing (a repository at the root, one it sits inside, ones below it, and the ahead/behind counts), `init_vault_repo()` / `create_repo_on_github()` / `link_vault_remote()` are the two routes onto GitHub, `sync_vault_repo()` commits, rebases and pushes — undoing a conflicted rebase before it returns — and `set_git_identity()` writes `user.name` and `user.email` for the whole machine, which is where `git_tooling()` reads them from, refusing an empty value or one starting with a dash before git is run. Creating the repository is the one thing git cannot do, so `gh` is used where it is installed and the browser where it is not; no token is ever held here. The output parsers (`commit_message()`, `remote_label()`, `repo_name_for_vault()`, `parse_ahead_behind()`, `failure_cause()`) are pure and unit-tested.
- **`src/single_instance.rs`** — Single-instance guard (Windows). The first launch holds a per-user named mutex and listens on a named pipe; a later launch detects the mutex, forwards its file path to the running instance (which opens it as a new tab and comes to the front), and exits before building any UI — so a second document reuses the existing process instead of spawning a whole new window and WebView2 group. A no-op on other platforms.
- **`src/png.rs`** — The PNG writer, and the only one in the project. `encode_rgba()` takes raw pixels and writes a palette image when the drawing has 256 colors or fewer — exact, since the palette holds the colors already there — and truecolor above that; every scanline goes out unfiltered, because the per-row filter heuristic other encoders use is built for gradients and costs bytes on flat interface pixels. `encode_rgba_paletted()` cuts a busier image down to 256 colors first, which is what a screenshot needs and no export ever asks for. `rgba_from_bmp()` reads the uncompressed bitmaps `scripts/capture-screenshot.ps1` writes, so the [diagram export](../01-features/07-editing.md#export) and the documentation screenshots go out through one encoder.
- **`src/platform.rs`** — Native OS integration, so no crate is carried for it: the clipboard and the Recycle Bin (Win32 `SetClipboardData` and `SHFileOperationW` on Windows, `pbcopy` and Finder on macOS), the installer download (`download_to()`, WinHTTP on Windows and the bundled `curl` on macOS, both using the OS certificate store), a request that can carry a method, headers and a body and hand back the status and headers, with one HTTPS check in front of both halves and one capped, jittered wait for a service answering "too many" — the Mac half passes every option over standard input rather than the command line, because `ps` there shows any process's arguments to every user on the machine and a token in one is a token published, the refresh token for a signed-in vault, kept in Windows Credential Manager or the macOS Keychain and never in a file this app writes, the stderr redirect `src/journal.rs` is built on (`redirect_stderr()`, `SetStdHandle` on Windows and a declared `dup2` on any Unix — three lines rather than a crate for one symbol), and the update applier — a detached copy of the binary that waits for the app to exit, re-verifies the staged installer, runs it, records whether it worked, and relaunches. Nothing here touches a copy left by another install context: two attempts at that each shipped broken, so the release notes ask instead.
- **`src/journal.rs`** — The app's log file, `journal.log` in the data folder ([Settings](../01-features/05-settings.md#files)). `start()` runs once at launch, before the window exists: it rolls the file aside at a megabyte keeping one previous copy, then hands it to `platform::redirect_stderr()` so every `eprintln!` in the app lands there, and replaces the panic hook so a crash does too. The Windows build opens no console, so without this all of that printing goes nowhere. Every failure is swallowed — an app that cannot write its journal still opens — and no document text is ever written to it, only paths.
- **`src/pipe.rs`** — The ask pipe: a local channel a running copy of the app answers questions on, so a bug can be looked at while it is happening instead of reconstructed from the journal afterwards. One JSON ask in, one JSON reply out, then the connection closes — a named pipe (`\\.\pipe\leaftext-journal-<user>`, `PIPE_ACCESS_DUPLEX`, where the single-instance pipe only ever listens) on Windows and a `UnixListener` in the data folder elsewhere, neither needing a crate. `Ask` is the whole vocabulary, written the way `IpcCommand` is: `log`, `state`, `eval`, `doc`, `edit`, `task`, `save`, `export`, `shot`, `gesture`, `idle`, `version`, `quit`, one variant and one arm each. An ask that is not in it is **refused with a message** rather than dropped, unlike the page's IPC — a page typo is our own bug, but a typo here is somebody waiting for an answer. `log` and `version` are answered on the pipe thread, because a hung app is exactly when they are wanted; `state` and `eval` go to the event loop carrying a reply channel and wait two seconds on it, so a loop too busy to answer costs the asker that and nothing else. `pipe_state()` takes the workspace rather than the whole `Reader`, which carries a window — that is what lets the answer be built in a test. `state` with `reader` set is that answer plus one `eval` of `window.leafReaderState()`: the scroll position, the block the reader is anchored to, which panels are up, the selection and whether a render is in flight, none of which the workspace holds — a visit's anchor is `None` until the reader leaves the document, so the app's own record is always one navigation behind. Two asks rather than one field, so a page that cannot reply costs the reader half and nothing else. `idle` polls that same function until the page says it has finished rendering, giving up inside the two seconds and saying which of the two it hit, so a driven pass reads the result instead of sleeping. This is `off_loop()` run backwards: that takes work off the window thread, this takes an answer off it. `eval` is the app's only use of `evaluate_script_with_callback` — every other script it runs is fire-and-forget — so the reply channel travels into the callback rather than being filled by the arm that starts it. It is the only ask that calls the page twice: `eval_ask.rs` sends the caller's line inside a `try` with a numbered mark declared after it, then reads that mark back, because the engine answers `null` for a script that threw, for one it never read and for one that honestly came to nothing alike, and only the mark tells the third from the first two. The reply is filled by whichever callback lands second, and once. **`eval` runs arbitrary JavaScript inside the app**, reachable by anything running as this user: the same bar as the single-instance pipe, which accepts only a file path where this accepts anything. It is also the whole reason the pipe beats reading the journal, and it is skippable — dropping the variant and its arm leaves the rest of the design unchanged. `doc`, `edit`, `task` and `save` are the document workflow, and the one path that changes a file without going through the page. They land on the same `EditableDocument` buffer, undo stack and `save_active_document()` the window's own editing uses, so a file written this way keeps the encoding and byte order mark it was read with — which is exactly what rewriting a file through terminal text output cannot promise, and the reason the workflow exists. Each is atomic and the pipe holds nothing between asks, so safety rides on a fingerprint rather than a session: every reply carries `source_fingerprint()` — `content_hash()` in hex, since the wrapper is JavaScript and a 64-bit integer loses its low bits on the way through `JSON.parse` — and both writes quote back the one they expect, a mismatch refusing the write and naming the fresh value. All three work the active tab, which is why `doc` brings its path to the front rather than editing behind the reader: the four functions they reuse take no tab index, and the switch is what keeps the window showing what an agent is touching. An edit re-renders through the reader's own `render()`, which restores a tab left in source from the same buffer — the code view's own `leafSourceUpdated` carries a dirty flag and no text, so the editor would have gone on showing the buffer it had. `task` is the shorter way through that workflow for the one edit a document does immediately: it checks or clears the `index`-th task and writes the file in the same ask, the way the reader's own checkbox does, so a checkbox is two calls rather than five and neither end computes a byte offset. `doc` answers a `tasks` list — every list marker in document order, each with its checked state and its own words — and that position is what `task` takes. It shares its whole body with the page's own `toggleTask`, which is what stopped that command writing a file when the index named no task: the marker is looked up before anything is spliced, and every refusal — a document not at the front, a moved fingerprint, a document that is not Markdown, an index naming no task — lands before a byte is written. It takes the resync the reader's checkbox takes rather than `edit`'s re-render, because one byte changed. `save` refuses an untitled document, because naming one opens a dialog that is the owner's to answer. `export` and `shot` are the two files the app makes that nothing here could otherwise read, because the button that makes them opens a dialog no session can answer: `export` renders the PDF and `shot` writes the picture, both at a path the asker names and both taking the page's own measurement of the sheet rather than working one out. They share the export's longer wait, since the render is inside the loop and the two seconds every other ask gets would report a stuck app over a file that was about to be written. `gesture` plays one pointer gesture into the page over the web view's own developer protocol — no cursor, no focus, no place on screen — which is what reaches a copy standing off every monitor, where a real mouse gesture is refused because a point on no monitor is clamped onto the desktop; its coordinates are the picture's own pixels, its walk is paced on a thread of its own and lands on the loop one step at a time, its wait stretches with the walk it names, and `type`/`key` are refused with `eval` named. `quit` is the only ask that ends anything, and it goes out through the same `shut_down()` the close button reaches, so the window's size, place and maximized state are saved — a killed process is the one exit that skips that. It is answered in **two** events rather than one: the loop says it heard, and the pipe thread sends `PipeCloseNow` once the asker has taken the reply. Stopping the loop ends every thread with it, and a reply still in the pipe at that moment is thrown away, so an arm that replied and then closed would report a clean close as the app failing to answer. That is why `answer()` hands back a `Reply` — the text, and an optional `AfterReply` the transport runs once the bytes are out — and why the transport takes a second function for it: it must not learn how to reach the event loop, and `serve()` is the one place that knows what closing means. A loop too wedged to answer refuses this the way it refuses `state`, and a kill is what is left for that.
- **`src/updater.rs`** — The staging model for [updates](../01-features/05-settings.md#updates): where a download lands, the length it must arrive at, the manifest a later launch reads it back from, and the record the applier leaves saying how the install went. `update_url_is_allowed()` holds the download to HTTPS and GitHub's own hosts, because the URL arrives from the network by way of the page and is handed to a native client that has no same-origin rule behind it.
- **`src/tests/`** — The library's unit tests, one file per subject with the shared helpers in `mod.rs`, rather than inline in `lib.rs`. They reach the crate's public and `pub(crate)` surface through `use super::*`. The binary's own tests are `src/app/tests/`, one file per subject with the shared helpers in its own `mod.rs`, and the store's are `src/store/tests.rs` — and a file's folder does not tell you which of those it belongs to, since `platform.rs` sits beside the library's files and is the binary's, so nothing here can see it.

it keeps no state of its own, because a variable here is still in its dead zone while the first render runs, and the first render is one of the things that closes it), the [full-window picture](../01-features/01-rendering.md#images) and the export beside it (`image-sheet.js` — the same overlay pointed at a picture the page already holds, so opening one reads no file, sends no command and a published site gets it for free; it carries no panel of its own, which is what lets a press anywhere but the picture read as a press on the dimmed page behind it. The export in the same corner is the other half of the file: it asks the host where the file goes, then hands back a document and a copy, a sheet to print, or a file its own canvas wrote — and it asks for the picture again in anonymous cross-origin mode rather than drawing the copy on screen, whose canvas is tainted and can never be read back), the [full-window table](../01-features/07-editing.md#inline-editing-the-reading-view) (`table-sheet.js` — the third of those overlays and the only one holding a copy rather than the page's own element, so closing it can write nothing; the copy's box wears `document-body` as well as its own class, which is what puts the table inside the scope the theme's link color and the dotted glossary underline are written behind, and the three declarations beside it are what that scope brings back that a sheet is not), the [first-launch bubble](../01-features/03-library.md#the-bubble-on-your-first-launch) (`hints.js` — a registry of name, target and one line of words, the placement pass that takes the first of four sides fitting the window whole, and the one-per-launch pacing; it sits right after `dom.js` so every fragment that registers a hint loads behind it), the minimap and reader scroll anchoring, the glossary sheet, theme wiring, and the updater. They are **one scope, not modules**: `APP_SHELL_SCRIPT_PARTS` in `lib.rs` concatenates them in order, because the page has no module loader. Order is therefore load-bearing — `journal.js` leads, because its `window.onerror`, `unhandledrejection` and `console.error` handlers are the only thing that sees a later fragment throw as it loads, and it posts to `window.ipc` directly since `send` in `dom.js` is a `const` in its dead zone until then; `state.js` follows, holding every mutable binding assigned from more than one fragment before any subject reaches it; the flowchart sheet's seven fragments come next, since everything else calls into them; and the last fragment ends with the bootstrap call that must run after everything else is defined. The joined script is **served as `app.js` over the [asset protocol](#bundled-asset-protocol)** behind the page's one script tag — written into the page by a browser host, appended by the desktop loader a painted frame later — because the shell reaches WebView2 as one string with a ceiling on it and the script was 88% of it — the page is now about 4% of the budget the test enforces. Nothing is substituted into the script, which is what lets it be a file. `just check-shell` boots the fragments joined in that order against a stand-in page, so a fragment that throws as it loads fails the build rather than opening a blank window.
- **`src/assets/reading.css`** and **`src/assets/reading/`** — the app stylesheet, as ordered parts. `READING_CSS_PARTS` in `reading_mode_css()` names them in cascade order and concatenates them with nothing between, so the join is one sheet character for character; it is served as `app.css` over `leaf-asset://` with the theme compiler's token blocks prepended. **A part is a contiguous run of lines, never a rule lifted out of one** — order inside the sheet is the cascade, so a part that reordered a line would change which of two equal-specificity rules wins. `scripts/reading-css.mjs` composes the same static cascade the binary does, so a check sees the declarations the reading rules consume rather than the rules alone: `parts()` and `whole()` cover `tokens.css`, then `icons.css`, then every `READING_CSS_PARTS` entry, with the binary's own added newline after each of the first two; `ruleParts()` is the narrower view for a check whose subject is the hand-written rules under `src/assets/reading/`; and `locate()` turns a place in the whole join back into a file and a line, refusing an added separator line that belongs to no file. It stops before the per-theme colors, which exist only once Rust has parsed the theme bundle and are covered by the Rust tests that read `reading_mode_css()` itself.
- **`src/assets/tokens.css`** and **`src/assets/icons.css`** — generated, never hand-edited: every value that does not change with the theme, and one mask class per icon. Each icon class reads `var(--lt-icon-<name>)` rather than carrying a drawing, so a theme family can redeclare the drawings its [icon pack](04-theming.md#icon-packs) covers. They are compiled from `design/` by `just bundle-tokens` and `bundle-icons`, which also write the color contract into `src/theme.rs`. See [Design system](05-design-system.md).
- **`src/assets/icon-packs/`** — the outside icon packs' drawings, one folder per pack and one `.svg` per icon name, copied in with each pack's license notice beside them under `src/assets/`. `bundle-icons` compiles them into the family blocks in `icons.css`; nothing is fetched at runtime.
- **`src/assets/theme-bootstrap.js`** — injected inline before first paint, so the theme resolves on the first frame rather than flashing the wrong one. Interface wording lives in the markup and the shell fragments, so there is nothing to look up before text appears.
- **`src/assets/desktop-front-end-loader.js`** — the desktop's front-end, inline at the foot of the page where a browser host carries the deferred tag. A deferred script still runs before the browser draws anything, so a launch reached a laid-out page with the startup card already parsed into it and then sat blank for the whole of the front end's own execution — interactive at 15ms, the script's bytes in at 41ms, and no pixel until it finished at 157ms. The loader preloads that same URL as parsing ends, so the local fetch stays alongside the first frame rather than moving behind it, and appends the script from the second animation-frame callback — one frame is painted between the two, and that frame is the card. Anonymous cross-origin on both, so the preload is the response the script reuses and a throw inside the front end still reaches `window.onerror` with its place. A browser host keeps the direct tag: a published site and an embedded document each start their own module boot underneath it, and that order is theirs.
- **`src/assets/themes.md`** — every theme's [palette as data](04-theming.md#palettes-are-data-themesmd), parsed once at startup. It's compiled from the editable `themes/` folder (one Markdown file per family, globbed) by `scripts/bundle-themes.mjs`; `just check-themes` guards the two against drift.

## Rendering pipeline

When a user opens a `.md` file, the following sequence runs entirely on the Rust side before any content reaches the WebView:

**1. Read the file**

`load_document()` or `opened_document_from_markdown()` in `lib.rs` reads the Markdown source from disk.

**2. Parse with pulldown-cmark**

`render_markdown_document()` parses the Markdown using `pulldown-cmark` with `Options::ENABLE_TABLES`, `ENABLE_STRIKETHROUGH`, `ENABLE_TASKLISTS`, `ENABLE_GFM`, `ENABLE_FOOTNOTES`, and `ENABLE_MATH` enabled.

**3. Apply GitHub extras**

A pipeline of event transformers adds heading IDs, linkifies plain URLs, resolves GitHub issue/PR references and emoji shortcodes, renders syntax-highlighted fenced code blocks via `syntect`, and handles footnote back-references.

**4. Sanitize with ammonia**

The raw rendered HTML is passed through `ammonia` with an allowlist of GFM-safe tags and attributes. Scripts, styles, event handlers, and dangerous URLs are stripped before the WebView ever sees the content. Attributes prefixed `data-leaf-` / `data-src-` are allowed through on every tag — the [editing](../01-features/07-editing.md) model's source-range markers, which carry no script and never reach a URL context.

**5. Inject initial settings**

`initial_settings_script()` produces `window.__leafSettings = {...}` from the persisted `Settings` struct. This script is registered as a WebView initialization script so the theme and library pane render from saved state on the very first paint — no flash of defaults.

`load_settings()` returns a `SettingsLoad`: the settings themselves plus whether a file was there that did not parse. The two are separated because they are otherwise indistinguishable — an unreadable file and no file at all both end in `Settings::default()`, so the app opens looking factory-fresh with nothing to say that someone's saved choices were skipped. `settings_unreadable_script()` carries that flag to the page as `window.__leafSettingsUnreadable`, and the boot growls once when it is true. A leading UTF-8 byte order mark is not one of those cases: Windows editors write one by default, so `read_config_text()` looks past it for both [config files](../01-features/05-settings.md#files).

`update_failed_script()` makes the same crossing for the same reason. `take_apply_outcome()` reads the detached applier's verdict at launch, before the event loop starts, so there is no page to send it to — it goes in as `window.__leafUpdateFailed`, and the boot composes the sentence from it and the running version. A [failed install](../01-features/05-settings.md#updates) relaunches the build that was already there, so nothing else on screen says which version is running.

**6. Load into the WebView**

`app_shell_html()` generates the page; the stylesheet and the front-end script are served beside it as `app.css` and `app.js`. The same router serves one more script, `app-evaluation.js` — the same fragments in the same order and the same shared scope, with a measure written around each of them — and only a copy launched by [`just probe-evaluation`](02-building.md#measuring-what-a-launch-costs) ever names it. `reading_mode_css()` assembles the complete style block: compiled theme CSS (from the bundled `themes.md`) + the stylesheet's own `:root` block of app-wide scales and metrics + application CSS. It is one call on `compose_reading_css`, which takes the icon sheet as an argument — the window gets the whole of it because a reader can change theme there, and `exported_page_css()` gets the same sheet with the five icon packs a pinned page can never wear cut out, sliced by the byte ranges `just bundle-icons` writes beside the sheet as `LEAF_ICON_PACK_RANGES`. Fonts are not bundled — the active [theme](../01-features/06-themes.md#fonts) fetches its font from Google Fonts on demand. The rendered document HTML is injected into the shell via `workspace_state_script()` or `workspace_switch_script()`, which call the appropriate `window.leaf*` JavaScript entry points.

## XML rendering pipeline

When a user opens a `.xml` file, `load_document()` detects the extension and calls `load_xml_document()` instead of the Markdown path:

**1. Parse with roxmltree**

`load_xml_document()` in `lib.rs` reads the XML source and `parse_xml()` in `xml.rs` parses it with `roxmltree` into a read-only DOM. Doctypes are allowed through (plists, XHTML and DocBook all carry one); roxmltree reads only the internal subset and never fetches anything. A file that isn't well-formed renders as a parse-error line naming the position, so the reader can go fix it.

**2. Route by content**

`render_xml_document()` sends a document with a `<TEI>` root or a `<teiHeader>` to the TEI renderer below, and everything else — sitemaps, RSS and Atom feeds, POMs, plists, exports, config files — to the generic renderer in `xml.rs`. The generic renderer works from the shape of the tree rather than any schema:

- an element holding only text (or only attributes) becomes a label/value field, and consecutive ones share a single two-column field list;
- two or more sibling records with the same tag, made only of short leaf values, become one table — a sitemap's `<url>` entries, a POM's `<dependency>` list;
- an element holding other elements becomes a section, headed by its own `<title>`/`<head>` child, by `Tag: name` for a `<name>` child or naming attribute, or by its humanized tag name (`lastBuildDate` reads as "Last build date");
- an element mixing text and markup renders as a paragraph of its text.

A document that names no title of its own — a sitemap has nowhere to say what it is — is headed and titled by its file name. Values that are entirely a URL become links.

**3. Pick the title and find the TEI body** (TEI only)

`render_tei_inner()` first reads every `titleStmt > title` and picks the document title by `type` and `xml:lang` — English main title, falling back to the English long title, then the first non-Tibetan title. The Sanskrit main title and the English and Sanskrit long titles render beneath the heading as a muted subtitle block; Tibetan titles are never shown. It then locates the `<text> > <body>` element and walks its child `<div>` elements recursively.

**4. Emit HTML** (TEI only)

`tei_render_div()` / `tei_render_node()` convert TEI elements to HTML equivalents: `<div type="chapter">` → heading, `<p>` → paragraph, `<lg><l>` → verse, `<note place="end">` → footnote reference collected in a `TeiCtx`. Heading slugs are produced by `tei_slugify()` to match the same GitHub-style slug algorithm used for Markdown headings.

**5. Append footnotes** (TEI only)

After traversal, any collected footnotes are appended as a `<section class="footnotes"><ol>…</ol></section>`, identical to the Markdown footnote format so the same CSS styles them.

**6. Auto-link glossary (optional)**

`auto_link_glossary()` walks up from the document's folder to the nearest `GLOSSARY.md` — `nearest_glossary_file` reads each folder and matches the name ignoring case, so the spelling on disk is what comes back, and it is the one lookup the `glossary:` sheet links use too — then wraps matched terms with `<a href="glossary:slug">` anchors — skipping text already inside a link, `code`, or `pre`. The identical pass runs for Markdown documents (the glossary file itself is exempt, so its entries are not self-linked).

**7. Inject into shell**

The finished HTML is handed to `app_shell_html()` and injected into the WebView exactly as Markdown output is — themes, minimap, pager, and scroll anchoring all apply unchanged.

## IPC bridge

Communication between the JavaScript running in the WebView and the Rust host uses `wry`'s IPC mechanism. JavaScript calls `window.ipc.postMessage(JSON.stringify(message))`. Rust deserializes the body into an `IpcCommand` using `serde_json` and forwards it unopened as `UserEvent::FromPage(...)` on the `tao` event loop, which handles it there. The command is described once: `UserEvent`'s own variants are only the signals the page cannot send — the watcher, a second launch, and answers coming back from worker threads.

## Key data structures

The following types model the reader's stateful document management. `Workspace` and `Tab` live in `src/app/workspace.rs`, the two history types in `src/app/history.rs`, `FileWatch` in `src/app/watch.rs`, and `ScrollAnchor` in `src/scripts.rs`:

- **`Workspace`** — holds `Vec<Tab>` (all open tabs) and `active: Option<usize>` (the currently visible tab index, or `None` when the home screen is showing).
- **`Tab`** — holds a `DocumentHistory`, a `ScrollHistory`, a `title` string (cached for the tab bar), an `Option<f64>` (the last saved code-view scroll fraction, restored when you return to a tab left in the [code view](../01-features/07-editing.md#code-view)), an `Option<EditableDocument>` (the [edit buffer](../01-features/07-editing.md#editing-the-source), created the first time the document is edited — inline in the reading view or via the code view — and kept so unsaved edits survive view toggles and tab switches), and a `code_view` flag for which view the tab is showing. The buffer outlives the window too: the close writes each dirty tab's text and its last-saved text into the [saved session](../01-features/05-settings.md#unsaved-edits), and the next launch reads the file, puts the buffer back where the two still agree, and drops it where the file has changed underneath. A tab holds one buffer wherever it has navigated since, so the entry names the document the words belong to rather than the one on screen — a session entry is one document with no back list, and words filed under a page the reader had walked on to would come back somewhere nothing on the window could reach. A buffer with no file behind it is carried on a flag of its own rather than by its path — the name a [new document](../01-features/07-editing.md#new-document) wears is a bare relative one, so asking whether it is a file would resolve it against the folder the app was started in — and it comes back as an empty buffer at that name with the carried words applied as one undoable replacement, no disk read anywhere in it. The reading position is not here: it belongs to the history step, one per document visited.
- **`DocumentHistory`** — a `Vec<DocumentVisit>` with a current index, each visit a path plus the `Option<ScrollAnchor>` the reader left that document at (`None` until they leave it). Supports `go_back()`, `go_forward()`, `stamp_current()` (the one place a position is written, called by a link click, Back, Forward and a tab switch), `current_anchor()`, and `forget_current()` (used when a file fails to open, which drops that visit's position with it).
- **`ScrollHistory`** — two `Vec<ScrollAnchor>` stacks (`back_entries` and `forward_entries`) that record in-document scroll jumps independently from document-level navigation.
- **`ScrollAnchor`** — `{ section: Option<String>, block: u32, offset_y: f64 }`. A render-stable position: the nearest heading `id` above the reader's top edge, the block ordinal within that section, and the signed pixel offset. Survives a full re-render because the same Markdown always produces the same block sequence.
- **`FileWatch`** — a debounced `notify` watcher (200 ms window) pointed at the active document's parent directory. Watching the parent rather than the file itself survives editors that save by atomic rename.

## Local image protocol

`local_image_protocol_response()` in `markdown/image_protocol.rs` serves local image files under the `leaf-image://` custom URL scheme (or `http://leaf-image.local/` on platforms where custom protocols are restricted, such as Windows and Android).

A path is resolved against the open document's directory and then read: a relative destination at any depth (`../../imgs/pic.png`), an absolute path, or a `file://` URL all work, so a document's images can live anywhere on disk. Missing files return `404 Not Found`; a read the OS itself refuses returns `403 Forbidden`.

URL segments carry the shape of the path. `__leaf_parent__` stands in for each `..` step, and `__leaf_absolute__/<encoded path>` carries a whole absolute path for images that do not sit under the document's directory. Because a Windows drive letter parses as a one-character URL scheme, `parse_image_destination_url()` treats a single-letter scheme as a path rather than a URL.

Responses carry `Cache-Control: no-store`, and the page adds a `?leaf-epoch=<n>` query — bumped on every render, and again whenever `image_refresh_script()` reports a changed file — because the web view otherwise keeps showing the copy it already decoded for that URL until the process restarts. The handler resolves the path from the URL's segments alone, so the query is inert on the way in. `is_local_image_path()` is what tells the watcher an image changed rather than a document: the file bytes are unchanged, so the [live reload](../01-features/02-navigation.md#reload) would hash-gate itself out, and the images are refreshed in place instead.

A response also carries `Access-Control-Allow-Origin: *`, and only where its type is one of the eleven kinds of picture the reading view draws. The page is served with `with_html`, so its origin is opaque and every custom-scheme answer is cross-origin to it: without that header the page cannot read a single pixel of a picture it is showing, which is what made [taking one out of a note](../01-features/01-rendering.md#images) in another format impossible. The condition is the whole of the decision — this handler reads whatever file the address resolves to, with no test that it is a picture, so an unconditional header would open every file on the disk to a fetch from the page, where the type holds it to pictures the page can already cause to be drawn. Nothing else about how a document's pictures are fetched changed: the export asks for the picture again, in anonymous cross-origin mode, rather than reading the copy on screen, whose canvas is tainted and always will be.

## The browser modules

`web/` is the renderer built as something a browser loads. It is the same crate — the same parser, the same sanitizer, the same block maps — with the desktop's dependencies switched off, so there is one renderer and not a second implementation of one.

More than one module, along two axes. The highlighter's syntax dumps and regex engine are most of the weight and most documents have no code in them, so a page downloads the core, renders, and fetches the colors only for a document that turns out to have a fenced code block — then renders that document again. A page that never fetches them keeps plain code, which is the same bargain as the four reads above. The other axis is the front end: two of the four builds carry the app's own page and script and two do not, so a product embedding an editor downloads the one with the front end and without the colors, and a published static site is served the one with both.

**The two published sites read through the core.** leaftext.com and empty.guru used to carry a hand-written copy of the renderer each, and the copies had stopped agreeing with each other and with the app. Now both draw their document bodies through this module and link the stylesheet it emits, while everything that draws the page *around* the document — the sidebar, the outline, the minimap, the code-block chrome, the settings menu, the glossary sheet — stays each site's own. Neither built file is committed anywhere: the publish workflow builds them and serves them beside the pages under `assets/leaftext/`, which is why `.gitignore` refuses that folder and `scripts/site-assets.mjs` is the one table naming those paths and saying what each of them is, read by the publish that writes them and by the local preview that answers them. The other site fetches the same files across origins, which GitHub Pages allows, so it needs no Rust and no build of its own. **The pictures are written the same way.** The repository keeps 61 PNG masters under `imgs/`, because the three hand-written PNG codecs all read them — the screenshot tool, the shot composer and the edge check; the publish encodes a lossless WebP beside each one and moves every page onto it, so a reader is served 3,318 KB rather than the 5,336 KB the masters weigh, without a pixel changing, and `scripts/site-images.mjs` is the one place that rewrite lives. **leaftext.com's front page is written the same way.** The repository keeps it with an empty content element and the publish renders the README into the copy it uploads, so a cold visitor reads the document out of the first response rather than after the module and a second fetch; the reader treats words already on the page as drawn and loads the module afterwards, for the glossary links alone. **Every fetch either site waits on runs under one deadline** (`site/fetches.js`): the wait dies after ten seconds with no byte arriving — while waiting for the answer and while its body streams — retries once on a fresh connection, and out of tries throws into the failure sentence each reader already carries. A stalled connection neither resolves nor rejects, so without it a page waited for ever and only a refresh got past it.

A page and a module share only memory and numbers, so strings cross as bytes: the page calls `leaf_alloc`, writes UTF-8 into what comes back, calls `leaf_render`, reads a little-endian `u32` length off the front of the answer, and frees both. `leaf_styles` hands over Leaftext's whole stylesheet — themes, tokens, icons and document rules — so an embedded document looks like a Leaftext document wherever it sits; a theme is chosen by stamping `data-leaf-theme` and `data-leaf-appearance` on the root element, exactly as the desktop's own page does. No binding generator is involved.

`just build-web` builds all four, loads each one and asks it what it is for — a document rendered through every module, the two carrying a front end asked for their page, their script, their boot state and the document call a page is served with, and the document buffer walked through every kind of edit against bytes the desktop's own buffer is held to — and holds the core to a size ceiling, since the reason for the split stops being true if the core drifts past it. It is not part of `just verify`, because it needs the `wasm32` target installed and a machine without one would fail having done nothing wrong. What the gate does run is `just check-web`, a plain type check of this crate at both feature ends: the workspace's only default member is the desktop app, so `cargo check --all-targets` never reaches the browser crate, and a library signature it no longer matches would otherwise stay green until somebody built for the browser by hand.

Behind the `shell` feature sit the app's own page and front end — `leaf_page`, `leaf_script`, `leaf_boot_script` — because a render-only embed has no use for half a megabyte of front end. That is what makes a published Leaftext site *the app* rather than a copy of it: the same page, the same script, the same stylesheet, with a browser host answering the commands a static site can answer. **The feature does not ask for the highlighter**, so `--features shell` is the module a product embedding an editor downloads and `--features shell,highlight` is the one a site is served.

**The same feature carries a document buffer, which is what makes an embedded document an editor rather than a picture of one.** Its arithmetic is the library's `EditableDocument` and none of it is repeated: one splice, one undo stack, one table rewrite, one field parser, the same code the desktop's own editing arms call. A buffer is opened by handle over the document's **bytes** — decoded the way a file read is, so the spelling is a fact about the document and the source can come back out spelled the way it went in — and every edit crosses as JSON, because two of them carry a list a numeric signature cannot hold. `web/buffer.json` pins the text after each kind of edit; a test beside the fixtures walks it through the desktop's buffer and the build recipe walks it through the built module, so a dispatch that reached another call fails rather than agreeing by luck.

**One front end, three hosts.** The page a reader touches is the same in all of them — a window, a published static site, and a document inside somebody else's product — so every command in `IpcCommand` is really more than one piece of work, and the browser's half used to be checked by nothing. `web/preview/host.js` and `web/embed/host.js` each carry a table with a row per command — answered, refused on purpose with the reason, or not yet with the ticket that owns it — and exports an `answers()` a page can ask before it draws a control. `just check-web-commands` reads the names off the enum, never off the front end, and fails on a command with no row **in either table**, a row naming no command, and a command the front end sends by name that no host has an arm for. Every host owes a line about every command, because they answer different halves of the app — a site cannot save and an embed can, an embed has no library and a site is one — so a command answered in one table while the other says nothing about it is a control that waits for ever in half the app. Writing that row is not optional politeness: the page raises a waiting state before it sends and clears it only when an answer arrives, so an unanswered command is not a dead control but one that waits for ever. `check-shell` then boots both hosts in the same fake page it boots the fragments in, which is the only thing that proves an arm still answers: the site's over a stand-in module with a real linear memory speaking the same length-prefixed protocol, and the embed's over a plain object, because the embed host is handed a module already loaded rather than loading one. **That host has no `import` in it on purpose** — the gate boots one by stripping its `export` keywords, so a host that imported anything could not be booted at all. What none of that reaches is a fault that appears only when the crate is built for `wasm32`; a tagged release builds every module for exactly that reason (see [Releasing](03-releasing.md#what-ci-builds)).

`just drive-web` presses things in it and reads the page back — the browser half of `just drive`, over the browser's own debugging port, no package added. **It tells the page it is focused before the first step, and reads the page's visibility after every one.** A headless page hides itself five to nine seconds in, and a hidden page runs no animation frame — which is where the front end does all of its placing, so a jump to a heading, a restore of a place and a reset to the top of a document are each called and do nothing while the click, the address and the element lookup all still report success. Focus emulation is the one call that holds it awake; `Page.bringToFront` and the two occlusion flags were measured and none of them does. A run whose page freezes anyway fails at the step that found it rather than passing in silence, and a healthy one says so once at the end. **A `size:` step lays the page out at a width of your choosing**, as often in one run as it is given, which is the only way anything here reads a page that is written to grow with the window: the browser opens at one size, and a reading taken without saying which width it was taken at is a reading of that one.

`just export-web` writes a folder of documents out as one of those sites: page, front end, module, vendored runtimes, the settings script, the document list, the documents, and the pictures those documents name. **Nothing serves it** — drop it on any static host. **A picture travels because a render asked for it**, not because its name looked like one: the export holds the same module the page renders through, so it renders each document, reads the addresses off the answer and copies whatever file sits behind each one — which is why there is no list of picture extensions here and why `format.rs` stays the one table of formats. Where those addresses point is the page's own doing: a site's page sits at the top and its documents sit under `source/`, so the boot tells the module that folder and the renderer joins it with the document's own before a relative address ever reaches a browser. A document inside somebody else's product is told nothing, because there the page is served from beside its own pictures and the address as written already resolves. Nothing above the folder the export was pointed at is addressable — a `..` that would climb out of it folds back to it — so a document naming a picture outside that folder draws the app's own broken mark, which is what that mark is for. `just preview-web` exports and then serves that folder locally, only because a page cannot fetch its neighbors off `file://`; it serves nothing the export does not contain. **leaftext.com is not that folder**, so it has a server of its own: `just preview-site` serves the repository root, bakes the front page in memory the way the deploy does, answers the three published files out of that same build so a page is never drawn through the copy the last publish left beside it, and writes nothing — the two share one small module holding the type table, the refusal of a path climbing out of whatever folder is being served, the address each hands out, and the answer itself — one handler taking the folder served and whatever is answered ahead of the disk, so the site preview is that handler holding its baked page and its three published files where the export preview holds nothing. **A preview prints the loopback address it bound rather than the name `localhost`, and refuses a port anything already answers on.** A program holding the whole of a port lets a loopback bind through with no error at all, so nothing may wait on the bind to report it — the port is asked on both loopback families first, and where either answers the server names what is there and stops rather than starting beside it and printing a line that opens somebody else's page.

**A site opens on its own front page, and says so when a file does not arrive.** The landing is the `readme.*` at the top of the export, else the `index.*` there, else whatever the listing serves first — matched however the author spelled it, and with no extension list of its own, since the export writes only documents the app reads. It is one function in the browser host, used twice: the boot hands it to the address opener as the fallback, so a document named in the address still wins, and the leaf at the bar's left opens the same answer, so the way back cannot disagree with the way in. That leaf is the whole of Home on a site — the desktop's start screen is recents and favorites, which a site has neither of. Every fetch the boot makes goes through one wrapper, so a listing, a document or the module that does not come back draws the start screen's own panel naming the file rather than killing the boot where nobody can see it: the two ways that happens are a folder opened straight off a disk, where a browser allows none of those fetches, and a publish that went out short.

**The shape of that page is `scripts/web-page.mjs`'s, not the export's.** One function over the page and the boot script, so what is injected and in what order can be read back from the shipped file rather than inferred from a chain of string replacements. `window.__leafSite` is the one boolean saying this is a site, and `window.__leafEmbedded` the one saying this is a document inside somebody else's product. The front end reshapes itself off either the way it reshapes off `window.__leafFrameless` in a frameless window — told on boot, because it draws the bar and the pane as it loads and a page that had to take them down again would show them first. An embed marks its body with a class the stylesheet reads, which takes the bar, the tab strip, the pane, the handle between them and the floating toolbar down together; a class rather than the site's node removal, because the bar and the pane are held by reference in fragments that know nothing about embedding, and a removed node is a null one of those. For a site: a site draws no Back, no Forward, no Open, no New document and no first-run bubble, because the browser has its own pair one row up, a static site has no file dialog and nowhere to save, and a reader who landed on a page has installed nothing. Those four are removed rather than hidden — a hidden button keeps its slot in the tab order and its listeners, and still sends a command nobody answers — so the binds that would have wired them are guarded, and the bar's fold, which captures its candidates as it loads, never carries a button that is gone into its menu. It draws no tab strip either — a site opens one document — and the library pane's folder trail is moved into the room the strip was holding, taking the vault switcher and the Sync button out of the pane with it. The same trail element, not a second one: the fitting pass, the refit on a width change and a crumb's click all measure and bind against whatever box it is standing in. Its chain is the open document's own path rather than the pane's folder, because nothing on a site reveals an opened file in the pane, so the two part company the moment a link is followed. Everything injected goes immediately above the page's own theme bootstrap, which is its first script tag and the only one carrying no attributes — below it, a restored theme lands after the first paint and nothing re-applies one. A page that stops leading with that tag is refused rather than injected into the wrong place.

**A site keeps a reader's choices; the desktop's page cannot.** `web/preview/settings.js` merges what the browser kept over the defaults the page was handed, and the host writes a key per command as it answers. The desktop's page is served on an opaque origin where `localStorage` throws, which is why its host injects settings instead — so this belongs beside the browser host and never in `src/assets/shell/`, which runs in both. A store that refuses the read, refuses the write, or holds a shape from another version leaves the site reading on defaults. The marks a reader makes are kept there too, and they are the one kept thing that is state rather than a setting — so they are merged back over the state the page was handed rather than over its settings, in the same file and above the same first paint. Three commands share that one key where every other kept choice owns its own, because marking, unmarking and reordering are three edits of one list; a mark whose document has left the export is answered out of the served listing, the way the desktop answers one whose file has moved.

## The Windows EXE installer

`installer/` is the third package in the workspace, and it exists because a machine whose policy blocks Windows Installer packages refuses an `.msi` whoever signed it. It links nothing of the app: it carries the built `leaftext.exe` inside itself, deflated by its build script from the path `LEAFTEXT_APP_EXE` names, and unpacks it at install time. Without that variable it still builds and still runs its tests, and refuses to install anything — which is what the release script's size check catches.

The install is data before it is an act. `plan.rs` is every file, every `HKCU` value, the one Start Menu entry and the Installed Apps record as a value a test can read on a machine that never runs it; `apply.rs` lays that plan down and takes it back up, adding order and refusal and nothing else. Both take an optional registry prefix, which is what lets a test drive a whole install and uninstall into a scratch key. The result is the same install `wix/main.wxs` produces — same folder, same values, same single entry, same associations — and `installer_claims_every_readable_extension` holds both installers to `format.rs`'s list, searching the MSI for the keys it names and reading the EXE installer's one table out whole.

`registry.rs` and `shortcut.rs` are the two things that touch the machine. A `.lnk` is a COM object saved to a file and `windows-sys` ships COM functions but no interface definitions at all, so `IShellLinkW` and `IPersistFile` are hand-written vtables — a page of declarations against a crate that would bring its own macro tree, for two interfaces. `ui.rs` is the one screen, drawn at `wix/main.wxs`'s own dialog units in the same Tahoma, so both installers show a person the same thing.

`launch.rs` is what happens once the install is laid down: a person who ran the installer themselves gets Leaftext opened, and a silent run opens nothing. It is a decision before it is an act, like the plan — a function over the request and the plan, answering with the app to open and the folder to open it from, so the rule is asserted without starting a process. Both paths come out of the plan's own Start Menu entry, so the installer and that entry provably open one file. `wix/main.wxs` carries the same rule as one custom action held to `UILevel=5 AND NOT Installed`, which is why the MSI opens nothing for the updater's `/qn`, for a scripted install, or for a repair.

Which of the two Windows files a copy updates through is written at install time, not chosen by a reader: the EXE installer leaves a marker beside the values the MSI already writes, and its absence means the MSI, because that is what every copy on disk before this looks like. Reading it is `platform.rs`'s job — the library compiles for a browser and must not reach the machine — and the binary hands the answer to the page. `just check-installer` type-checks and tests this package, for the same reason `check-web` exists: the workspace's only default member is the desktop app.

## Bundled asset protocol

A second custom scheme, `leaf-asset://` (`http://leaf-asset.local/` where custom protocols are restricted), served by `bundled_asset_response()` in `assets.rs`, provides the renderer's vendored runtimes — the Mermaid bundle, the KaTeX script and stylesheet, the KaTeX WOFF2 fonts, the Monaco editor and stylesheet behind the [code view](../01-features/07-editing.md#editing-the-source), and the PixiJS + d3-force bundles behind the [Graph view](../01-features/03-library.md#graph) — along with the app stylesheet and the [flowchart editor](../01-features/07-editing.md#the-flowchart-editor)'s own script, both of which are ours rather than vendored and are served here to keep them out of the shell string — straight from bytes compiled into the binary with `include_bytes!`. Diagrams, math, the source editor, and the graph therefore render fully offline, with no CDN dependency. The Content-Security-Policy restricts script sources to `'self'` plus this protocol; style and font sources also allow Google Fonts (`fonts.googleapis.com` / `fonts.gstatic.com`), from which the active [theme](../01-features/06-themes.md#fonts) fetches its font. The graph and editor runtimes load lazily — only the first time their view opens — and a Pixi companion bundle swaps its `new Function` shader/uniform paths for eval-free polyfills so it runs under that CSP. Every response over the scheme carries `Access-Control-Allow-Origin: *` and every script tag fetching one asks for it in anonymous cross-origin mode, which is the pair that lets a throw inside one of these scripts reach `window.onerror` with its message, file and line instead of the browser's masked `Script error.` — the bytes are the app's own and already running in the page, so the read reveals nothing new. Each asset URL carries the build's version as a query, because the web view keeps a response's headers with its bytes for a year: without it a copy that cached an asset under the older headers would go on answering with them, which is how the pair once shipped with the throws still masked.

A third, `leaf-source://`, carries the [code view](../01-features/07-editing.md#code-view)'s payload: the exact buffer text, which is the whole of it now that the editor colors its own lines. It exists because `evaluate_script` is the wrong shape for megabytes: the whole script crosses the webview's process boundary, which measured over four seconds of a large file's entry, and `JSON.parse` in place of an object literal changed nothing, because the cost is the crossing rather than the parse. The host stages the payload, hands the page only a URL, and the renderer fetches it. The response carries `Access-Control-Allow-Origin` — the scheme is a different origin from the page, so without it the fetch is refused before the first byte — and `connect-src` names that origin, which is the only reason it appears in the Content-Security-Policy. One payload is held at a time: staging the next supersedes it, and a stale URL gets a 404 rather than old source.
